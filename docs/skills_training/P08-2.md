## 一、案例介绍

### 1.1 物理背景

在分布式任务处理系统中，重试机制是容错的核心手段。当任务执行失败（网络超时、临时资源不可用、下游服务抖动）时，系统会自动重试以保证最终一致性。然而，如果重试逻辑设计不当，会导致**同一任务被多次处理**，引发数据不一致、资源浪费、甚至业务逻辑错误。

### 1.2 事故场景

**系统架构**：
- 任务队列：RabbitMQ（持久化队列）
- 消费者：Python worker 进程（多实例部署）
- 数据库：PostgreSQL（存储任务状态与处理结果）
- 任务类型：船舶阻力计算任务（输入几何参数，输出阻力系数）

**关键参数**：
| 参数 | 值 | 说明 |
|------|-----|------|
| 任务超时 | 30s | 超过此时间认为任务失败 |
| 最大重试次数 | 3 | 指数退避：1s, 2s, 4s |
| 消费者并发数 | 4 | 每个 worker 实例 |
| ACK 模式 | manual | 处理成功后手动 ACK |

### 1.3 事故时间线

详见 [incident_timeline.md](P08-2/incident_timeline.md)

**关键事件**：
- T+0s：任务 #A1B2C3 入队，worker-1 开始处理
- T+28s：数据库写入中间结果（耗时较长）
- T+31s：RabbitMQ 认为任务超时，重新投递给 worker-2
- T+32s：worker-1 完成处理，发送 ACK（但消息已被重新投递）
- T+33s：worker-2 开始处理同一任务
- T+35s：worker-2 完成处理，再次写入数据库
- **结果**：任务 #A1B2C3 被处理两次，数据库中出现重复记录

## 二、怎么做的（根因分析与修复）

### 2.1 根因分析

**直接原因**：
1. RabbitMQ 的 ACK 超时机制与任务实际执行时间不匹配
2. 任务处理逻辑缺乏幂等性保护

**深层原因**：
1. **ACK 时机错误**：应该在任务开始前 ACK（at-most-once）或完成后 ACK（at-least-once），但当前实现是"处理中 ACK"，导致超时后消息被重新投递
2. **缺乏幂等键**：任务处理逻辑没有使用唯一键（如任务 ID）防止重复处理
3. **数据库约束缺失**：没有在数据库层面设置唯一约束

### 2.2 修复方案

详见 [code_changes.md](P08-2/code_changes.md)

**三层防护**：

#### 第一层：消息队列层
```python
# 修复前：处理完成后 ACK（超时会被重新投递）
def process_task(task):
    result = compute(task)
    channel.basic_ack(delivery_tag)  # 太晚了！

# 修复后：任务开始前 ACK + 本地状态追踪
def process_task(task):
    task_id = task['id']
    if is_already_processing(task_id):
        logger.warning(f"Task {task_id} already in progress, skipping")
        channel.basic_ack(delivery_tag)
        return
    
    mark_as_processing(task_id)
    channel.basic_ack(delivery_tag)  # 立即 ACK，防止超时重投
    try:
        result = compute(task)
        save_result(task_id, result)
    finally:
        mark_as_completed(task_id)
```

#### 第二层：业务逻辑层（幂等性）
```python
# 使用任务 ID 作为幂等键
def save_result(task_id, result):
    # INSERT ... ON CONFLICT (task_id) DO NOTHING
    db.execute("""
        INSERT INTO task_results (task_id, result, created_at)
        VALUES (%s, %s, NOW())
        ON CONFLICT (task_id) DO NOTHING
    """, (task_id, json.dumps(result)))
```

#### 第三层：数据库层（唯一约束）
```sql
-- 添加唯一约束，防止重复插入
ALTER TABLE task_results 
ADD CONSTRAINT uk_task_id UNIQUE (task_id);
```

### 2.3 回归测试

详见 [regression_tests.py](P08-2/regression_tests.py)

**测试用例**：
1. **正常处理**：任务成功处理一次
2. **重试去重**：同一任务被投递两次，只处理一次
3. **并发去重**：多个 worker 同时收到同一任务，只处理一次
4. **失败重试**：任务失败后重试，最终成功处理一次

## 五、注意点（踩坑与局限）

### 5.1 踩过的坑

1. **ACK 时机陷阱**：
   - ❌ 错误：处理完成后 ACK（超时会被重投）
   - ❌ 错误：任务开始前 ACK（失败会丢失）
   - ✅ 正确：任务开始前 ACK + 本地状态追踪 + 幂等性保护

2. **幂等性实现陷阱**：
   - ❌ 错误：仅依赖应用层去重（并发场景会失效）
   - ✅ 正确：应用层 + 数据库层双重保护

3. **唯一约束陷阱**：
   - ❌ 错误：在业务字段上建唯一约束（如 `result_hash`，可能冲突）
   - ✅ 正确：在任务 ID 上建唯一约束（天然唯一）

### 5.2 适用范围

**适用场景**：
- 消息队列 + 多消费者架构
- 任务处理时间不确定（可能超时）
- 需要保证 exactly-once 或 at-least-once 语义

**不适用场景**：
- 实时流处理（延迟敏感，无法容忍额外检查）
- 无状态计算（重复处理无副作用，如纯函数计算）
- 单消费者场景（无并发问题）

### 5.3 局限性

1. **性能开销**：幂等性检查增加约 5-10ms 延迟（可接受）
2. **存储开销**：需要维护任务状态表（长期运行需定期清理）
3. **复杂度增加**：三层防护增加系统复杂度，需要充分测试

## 附录：可复用规程（Runbook）

### A.1 适用边界

- 消息队列系统（RabbitMQ/Kafka/Pulsar）
- 任务处理时间 > 消息超时的场景
- 需要保证数据一致性的业务

### A.2 出处

- **代码变更**：[code_changes.md](P08-2/code_changes.md)
- **回归测试**：[regression_tests.py](P08-2/regression_tests.py)

- **日志摘录**：[log_excerpts.md](P08-2/log_excerpts.md)

### A.3 机制

**三层防护机制**：
1. **消息队列层**：立即 ACK + 本地状态追踪
2. **业务逻辑层**：幂等键 + UPSERT 语义
3. **数据库层**：唯一约束

### A.4 可复用规程

**检查清单**：
- [ ] 消息 ACK 时机是否正确？
- [ ] 任务处理逻辑是否幂等？
- [ ] 数据库是否有唯一约束？
- [ ] 是否有并发去重测试？
- [ ] 是否有重试去重测试？

**实施步骤**：
1. 审计现有消息处理逻辑，识别 ACK 时机问题
2. 添加幂等键（通常为任务 ID）
3. 实现 UPSERT 语义（INSERT ... ON CONFLICT DO NOTHING）
4. 添加数据库唯一约束
5. 编写回归测试（并发 + 重试场景）
6. 压力测试验证

### A.5 反例与局限

**反例**：
- ❌ 仅依赖应用层去重（并发场景失效）
- ❌ 在非唯一字段上建约束（如 `result_hash`）
- ❌ 处理完成后才 ACK（超时重投）

**局限**：
- 增加 5-10ms 延迟（通常可接受）
- 需要维护任务状态表（需定期清理）
- 系统复杂度增加

### A.6 可机械检测的护栏

**自动化检查**：
```bash
# 1. 检查消息处理函数是否有幂等键
grep -r "def process_" src/ | grep -v "task_id"

# 2. 检查数据库表是否有唯一约束
psql -c "\d task_results" | grep "UNIQUE"

# 3. 检查是否有并发去重测试
grep -r "test_concurrent" tests/

# 4. 监控重复处理率
SELECT COUNT(*) * 100.0 / (SELECT COUNT(*) FROM task_results) 
FROM task_results 
GROUP BY task_id 
HAVING COUNT(*) > 1;
```

本次训练通过一个真实的「重试导致重复处理」事故，蒸馏出了可复用的 runbook：

1. **根因**：ACK 时机错误 + 缺乏幂等性保护

- 代码扫描：检查幂等键使用
