```

    ├ INSERT tensor_dev_missions(...)     ← 未显式给 status，取 DB 默认 'queued'
    ├ INSERT tensor_agent_sessions('active')
    ├ append_event(session,'plan')
    └ return {"status":"queued"}          :218   ← 装饰器无 status_code ⇒ HTTP 200
                                                  （全仓无任何路由返回 202，见 §3-C3）

[2] POST /tensor/missions/claim           :506  claim_mission()
    ├ 前置：require_factory_agent + 组织解析
    ├ 会话绑定校验（带 agent_session_id 时）：
    │   注册表 factory_resident_workers 的 (model, role) 与呈递值不一致 ⇒ 409
    │   code=session_config_drift（:515-530，2026-11-07 IN27 事故后加的机器可读化）
    ├ 只在飞单冲突 ⇒ {"claimed":false,"busy":true} :532

[5] POST /{id}/complete :797
    ├ 仅 running 可完（awaiting_acceptance/终态 ⇒ 409）
    ├ 成功必须请求验收（acceptance=True），否则 422

    ├ acceptance=True ⇒ status='awaiting_acceptance' + 建 pending 审批单 :886-900

[6] POST /tensor/approvals/{aid}/decide   backend/api/tensor_approvals.py:210+
    └ dev_acceptance：approved→succeeded / rejected→failed（唯一把
       awaiting_acceptance 变终态的代码路径；需要 ADMIN 角色）
```

**可收养性（claimability）是被 5 个过滤子句同时决定的乘积**：

| 过滤子句 | 语义 | 单侧设置（受理时） | 谁能领到 |
| --- | --- | --- | --- |
| `runner` | 车道分类 | `runner='native'` | 只呈递同 runner 的 daemon |
| `model` | 模型引脚 | `model='glm-5.1'` | 该 model 的 daemon；`NULL` 只被 `claim_null_model=true` 的 daemon 领 |
| `worker_role` | 角色车道 | `worker_role='data'` | 呈递同 role 的会话；**未呈递 role 的 daemon 只领 `worker_role IS NULL`**（:575） |
| `agent_session_id` | 会话专属 | 受理时带了 session id | 只被该 session 领（除非 `claim_unassigned=true`） |
| `dependency_ids` | 依赖门 | 依赖里含**不存在的 id** | **永不可领**（`prerequisite.id IS NULL` ⇒ NOT EXISTS 恒假） |

**没有任何「排队超时」清扫器**：`tools/agent/gc.py:10` 明确把 `queued` 归入
`keep (active)`，生产库里也没有把老 `queued` 判 failed 的路径 —— 一旦上述乘积为假，
该单**永久停在 queued**，且对外部观察者只表现为「队列变老」。

## 3. 三分类

### 已证实（REAL，代码/只读库证据可直接复算）

- **C1 受理端点不返回 202**。装饰器 `:133` 无 `status_code`；全仓 `grep 'status_code=202|HTTP_202'` 命中 0；
  `/batch` 路由是 201。用户看到的「202」不是本服务产生的（见 I1）。
- **C2 受理只写 `queued`，不校验可收养性**。受理路径只做组织/角色/幂等/预算校验，
  从不检查是否**存在**能领它的车道（model/runner/role/session 是否有 enabled 认领者）。
  即「受理成功」与「可被领走」是两个独立事实。
- **C3 领取失败是静默空手**（`:620` 仅 `{"claimed": false}`），无 `reason`/`code`，
  运维面拿到的是二值，无法区分「池空」与「被过滤掉」。
- **C4 五子句乘积 + 无排队超时**（§1 表 + `gc.py:10`）⇒ 不可收养的单**永久 queued**。
- **C5 `worker_role` 缺省即 `worker_role IS NULL`**（`:575`）：受理时写了 role 的单，
  对「只呈递 model、不呈递 role」的 daemon 完全不可见 —— 这是代码里最锋利的一处隐式收窄。
- **C6 依赖门对不存在的依赖 id 恒阻塞**：`prerequisite.id IS NULL` 使 NOT EXISTS 永真。
- **C7 `awaiting_acceptance` 不是终态**：唯一出边是 ADMIN 的 `/approvals/{id}/decide`
  （`tensor_approvals.py:210+`）。worker 干完活、报告发了，用户侧仍看到「未完成」。
- **C8 现场签名（本次只读 SQL，2026-11-07T22:0xZ）**：`queued=51`，
  其中 **45 单引脚 `model='glm-5.1'`（最老 668 min）**，6 单 `model IS NULL`（最老 **725 min**）；
  `awaiting_acceptance=1`。注册表里 `glm-5.1` 唯一注册者 `tp-gen-4` enabled、state=idle、
  **心跳 1 min（新鲜）**，而该 model **最近一次真实认领证据是 9693 min（≈6.7 天）前**；
  同池 `deepseek-v4-flash` 车道 40 个 enabled 注册者、心跳 0 min、最近认领 0 min（活着），
  却领不走那 6 张 `NULL` 引脚单（没人呈递 `claim_null_model`）。
  ⇒ **「心跳新鲜 ≠ 可认领」在生产库上此刻成立**，与 2026-11-07 IN27 诊断单同一签名。

### 推断（INFERRED，有强证据但未逐跳验证）

- **I1 用户看到的 202 来自中间层或客户端假设**：本服务无 202 出边；最可能是反向代理/网关
  或前端把「异步受理」硬编码成 202 后，用户据此认为走到了异步队列。
  未逐一核对代理配置（本单未读 nginx/ingress 全量配置）⇒ 停在推断。
- **I2 45 张 glm-5.1 单是**「该车道无真认领者」而非「池子太深」：证据是同时刻其他车道
  认领延迟 0–1 min，且 glm-5.1 车道 6.7 天零认领证据。差异 3 个数量级，机制上只能是过滤而非拥塞。
- **I3 6 张 NULL 单因 `claim_null_model=false` 被饿死**：所有 resident 都呈递了具体 model，
  没有任何进程以 `claim_null_model=true` 运行（注册表无该字段，需读 daemon 启动参数才能确认）。

### 未知（UNKNOWN，本单未取到证据）

- **U1** 45 张 glm-5.1 单的**业务归属**（是否为已作废/停挂应删的单）——未逐单读 `goal`。
- **U2** `tp-gen-4` 进程实际启动参数（`--model` 是否已漂到别的 model）：需读节点进程表，
  本工作树外，未取证。
- **U3** 代理层 202 的真实来源（I1 的最后一跳）。
- **U4** 是否存在**历史**端到端闭合演练（不在代码仓内，可能在运维 runbook）。

## 4. 最小下一步（按性价比排序，均可逆、不改状态机语义）

1. **给「空手」以原因码**（最小、收益最大）：`claim_mission` 在 `claimed:false` 时回填
   `{"needed": {runner, model, worker_role, session}, "queued_total": n, "queued_matching_after_each_filter": {…}}`，
   让「受理了却永不完成」自证。**不新增状态、不改过滤器**，纯可观测性。
2. **受理侧的可收养性预检（warn-only）**：`POST /tensor/missions` 返回体加
   `claimable_by_live_lane: true/false` + `lane_evidence`（近 6h 是否有该 (model,role,runner)
   的认领证据，复用 `queue_adoption.pin_audit` 的 `lane_alive` 口径）。受理即告知
   「这单现在没人能领」，而不是让用户 12 小时后才发现。
3. **排队老化告警（不自动失败）**：把 `queue_adoption.split_backlog` 的
   `oldest_adoptable_minutes > 240` 接成告警事件；**不要**自动把老 queued 判 failed
   —— 会误杀停挂/依赖等待单（IN27 已证明口径错会造假越界）。
4. **补一条状态机闭合测试**（现为空白）：accept→claim→start→complete(acceptance)→decide，
   断言终态可达；再补两条负控：`worker_role` 不匹配的 daemon 领不到该单、
   依赖含不存在 id 的单不可领（把 C5/C6 从「读代码才知道」变成「跑测试就知道」）。
5. 现场处置（运维动作，非本单）：对 45 张 glm-5.1 单 `unpin`（`result.model_unpinned_from`
   可回滚）或给该 model 重启一个真车道；对 6 张 NULL 单派一个 `claim_null_model=true` 的默认 daemon。
