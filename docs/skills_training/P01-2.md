## 1. 目标（Goal）

将「让这个服务更好」这一模糊诉求，转化为一份**可检验的变更契约**——以平台任务队列偶发超时为例，明确定义：目标、受益人、现状与基线证据、可观测目标行为、验收判据、非目标、假设与未知、风险。

**核心产出**：一份机器可裁的变更契约，任何后续实施者（人或 AI）可据此判断变更是否成功，无需依赖主观评价。

---

## 2. 受益人（Beneficiaries）

| 角色 | 痛点 | 受益方式 |
|---|---|---|
| 常驻 Agent（tp_worker 舰队） | 领取任务时偶发超时/静默失败，导致任务积压、战役 DAG 阻塞 | 领取路径可观测、超时原因可归因、恢复路径明确 |
| 战役编排器（campaign_dispatcher） | 依赖任务按时领取推进 DAG 节点；超时导致 sync 周期拉长、提案波延迟 | 超时事件可被 dispatcher 感知并触发降级策略 |
| 平台运维（operator） | 超时发生后需人工排查日志、区分"真死"与"假死" | 超时分类自动产出，减少 MTTR |
| 任务派发者（owner/agent） | 无法区分"任务无人领"与"任务被领但超时" | 队列状态可观测，派发决策有数据支撑 |

## 3. 现状与基线证据（Current State & Baseline Evidence）

### 3.1 架构概览

平台任务队列采用 **PostgreSQL + 乐观锁（FOR UPDATE SKIP LOCKED）** 模式，无独立消息中间件。核心链路：

```
Agent Daemon → POST /tensor/missions/claim → DB (UPDATE ... FOR UPDATE SKIP LOCKED) → 返回 claimed mission
```

### 3.2 已知超时点与超时值

| 超时点 | 位置 | 当前值 | 来源 |
|---|---|---|---|
| 认证登录 | `campaign_dispatcher.py:get_token()` | 30s | `urllib.request.urlopen(timeout=30)` |
| API 调用 | `campaign_dispatcher.py:api()` | 60s | `urllib.request.urlopen(timeout=60)` |
| 心跳静默收割阈值 | `tensor_missions.py:claim_mission()` | 240s | SQL: `heartbeat_at > now()-interval '240 seconds'` |
| 进程启动宽限期 | `tensor_missions.py` 模块级常量 | 300s | `_CLAIM_REAP_BOOT_GRACE = timedelta(seconds=300)` |
| Agent 总超时 | `agent.py` | 45s（可配 10-90s） | `AGENT_TOTAL_TIMEOUT_SECONDS` |
| 工具调用超时 | `agent.py:execute_tool()` | 5s | `timeout_seconds=_remaining_seconds(deadline, cap=5.0)` |
| LLM 调用超时 | `agent.py:_call_zhipu()` | 动态（剩余时间） | `timeout_seconds=_remaining_seconds(deadline)` |
| Git 子进程超时 | `campaign_dispatcher.py:_hollow()` | 15s | `subprocess.run(..., timeout=15)` |
| SQL 子进程超时 | `campaign_dispatcher.py:q()` | **无** | `subprocess.run(PSQL + [sql])` 无 timeout 参数 |

## 4. 可观测目标行为（Observable Target Behavior）

变更生效后，以下行为应可被外部观测（无需侵入代码）：

### 4.1 超时分类可观测

每次 claim 请求的超时事件应被分类为以下之一：

| 类别 | 判定条件 | 含义 |
|---|---|---|
| `auth_timeout` | 登录请求 >30s 无响应 | 认证服务不可用 |
| `api_timeout` | API 请求 >60s 无响应 | 后端处理超时 |
| `sql_timeout` | psql 子进程 >30s 无返回 | 数据库查询超时（当前无超时保护） |
| `heartbeat_stale` | 心跳静默 >240s | Agent 可能已死或网络分区 |
| `boot_grace_skip` | 进程启动 <300s 内跳过收割 | 正常保护行为 |
| `orphan_pin` | 队列中某 model 无活体 worker | 车道死亡，任务被钉死 |

### 4.2 队列健康度可观测

以下指标应可通过 SQL 或 API 直接读取：

```sql
-- 可收养队列最老年龄（分钟）
SELECT EXTRACT(EPOCH FROM (now() - MIN(created_at)))/60
FROM tensor_dev_missions
WHERE status = 'queued' AND suspended_at IS NULL;

-- 各 model 车道存活状态
SELECT model, COUNT(*) as queued_count,
       MAX(heartbeat_at) as last_heartbeat
FROM tensor_dev_missions m
LEFT JOIN factory_resident_workers w ON m.model = w.model
WHERE m.status = 'queued' AND m.suspended_at IS NULL
GROUP BY model;
```

### 4.3 超时恢复路径可观测

超时发生后，系统应自动执行以下恢复动作之一（可被日志追踪）：

1. **auth_timeout** → 重试登录（最多 2 次）→ 仍失败则记录事件并跳过本轮 dispatch
2. **api_timeout** → 记录事件，下一轮 30s 周期自动重试
3. **sql_timeout** → （当前缺失）应记录事件并标记该 claim 周期为"数据不可信"
4. **heartbeat_stale** → lazy reap → 任务回 queued → 下一轮可被重新领取
5. **orphan_pin** → 记录事件 → 提案波触发模型切换

## 5. 验收判据（Acceptance Criteria）

以下判据全部为**机器可裁**，不依赖主观判断：

### AC-1：超时分类覆盖率 ≥ 95%

**方法**：注入 100 次模拟超时事件（覆盖 6 类），验证每类均被正确分类。

**判据**：
```
correct_classifications / total_injected >= 0.95
```

**测量方式**：pytest 测试套件，使用 mock 注入超时场景。

### AC-2：SQL 子进程超时保护

**方法**：对 `campaign_dispatcher.py:q()` 添加 timeout 参数（建议 30s）。

**判据**：
- 注入慢 SQL（`SELECT pg_sleep(35)`），子进程在 30±2s 内被终止
- 不引发守护进程崩溃（捕获异常并记录日志）

### AC-3：队列年龄指标口径正确

**方法**：构造包含停挂单、孤儿引脚、正常单的混合队列。

**判据**：
- `split_backlog()["violating"]` 仅对 adoptable 单判断
- `split_backlog()["oldest_adoptable_minutes"]` 与手工计算一致（误差 < 0.1 min）
- `pin_audit()["orphan_pins"]` 正确识别无活体 worker 的 model

### AC-4：启动宽限期不误杀

**方法**：模拟后端重启后 300s 内的 claim 请求。

**判据**：
- 重启后 0-299s 内：`reaped` 列表为空
- 重启后 300s+：正常执行 lazy reap

### AC-5：超时事件可追溯

**方法**：触发一次超时，检查 `campaign_events` 表。

**判据**：
- 事件类型在白名单 `_EV_ALLOWED` 内
- 事件 detail 包含超时类别、时间戳、受影响 mission ID

## 6. 非目标（Non-Goals）

以下内容**明确排除**在本次变更范围之外：

| 排除项 | 理由 |
|---|---|
| 替换 PostgreSQL 为 Redis/RabbitMQ | 架构级变更，需独立提案 |
| 修改心跳阈值（240s） | 阈值调优属运维参数，非本契约范围 |
| 修改启动宽限期（300s） | 同上 |
| 修复孤儿引脚的根因（model 注册漂移） | 属 IN20-R4 已立案的独立问题 |
| 修改停挂单的状态修复 | 属 queue_adoption.py 的 heal_plan 范围 |
| 性能优化（claim 延迟 <100ms） | 当前 claim 延迟非瓶颈，超时才是 |

## 7. 假设与未知（Assumptions & Unknowns）

### 7.1 假设

| # | 假设 | 验证方式 |
|---|---|---|
| A1 | PostgreSQL 连接池充足（无连接耗尽导致的"伪超时"） | 查 `pg_stat_activity` 中 `wait_event_type` |
| A2 | 网络延迟 <50ms（同机部署） | `ping 127.0.0.1` |
| A3 | Agent daemon 进程存活时心跳可正常发送 | 查 `/var/log/tp-fleet/` 日志 |
| A4 | `campaign_events` 表可写（无磁盘满/权限问题） | 手动 INSERT 测试 |

### 7.2 未知

| # | 未知 | 影响 | 探索计划 |
|---|---|---|---|
| U1 | 生产环境实际超时分布（各类占比） | 无法确定优先级 | 需部署超时埋点后观察 1 周 |
| U2 | 高负载下（>50 并发 claim）的锁竞争情况 | SKIP LOCKED 在极端并发下的行为 | 需压力测试 |

| U4 | 多组织（organization_id > 1）下的队列隔离是否完整 | 可能跨组织误领 | 需审计 claim SQL 的 org 过滤 |
