# 变更契约：平台任务队列偶发超时治理

> 本文档为 Skills 训练 P01-1 产物，遵循 problem-framing 技能 Procedure。
> 主题：将「让这个服务更好」转化为一份可检验的变更契约。
> 案例：平台任务队列偶发超时。
> 纪律：不提出任何代码改动。

---

## 1. 目标（Goal）

将平台任务队列（`tensor_dev_missions` 表驱动的 mission 派发与执行链路）中**偶发超时**现象的发生率从当前基线降低至可接受阈值，并建立可观测、可复现、可回归验证的超时治理闭环。

具体而言：
- 明确超时的定义边界（哪些超时算、哪些不算）
- 量化当前超时发生率与分布特征
- 设定可测量的改善目标
- 划定验收判据，使任何后续改动都能被客观判定为「有效」或「无效」

---

## 2. 受益人（Beneficiaries）

| 角色 | 受益方式 |
|---|---|
| **任务派发者（Dispatcher / Campaign 调度器）** | 减少因超时导致的任务状态不确定（`claimed` 卡死、`running` 无结果），降低重试与人工干预成本 |
| **执行智能体（Agent Worker）** | 获得更合理的超时预算分配，避免因上游超时被误判为失败 |
| **平台运维（Ops / SRE）** | 超时事件可观测、可告警、可追溯，减少 on-call 排查时间 |
| **任务提交方（Mission Submitter）** | 批量提交（batch mission）时获得更可靠的原子性保证，减少部分成功部分超时的中间态 |
| **平台所有者（Owner）** | 整体任务完成率提升，campaign 轮转周期缩短 |

---

## 3. 现状与基线证据（Current State & Baseline Evidence）

### 3.1 系统架构概览

平台任务队列由以下组件构成：

```
Mission Submitter → POST /tensor/missions (或 /batch)
    → tensor_dev_missions 表 (status: queued → claimed → running → succeeded/failed)
    → Agent Worker 领取任务 (claim)
    → 执行链路 (tool calls, LLM calls, cluster jobs)
    → 结果回写 (result JSON)
```

### 3.2 已知超时点（代码审计发现）

| 位置 | 超时设置 | 超时行为 | 证据等级 |
|---|---|---|---|
| `backend/api/agent.py` — Agent 总超时 | `AGENT_TOTAL_TIMEOUT_SECONDS`，默认 45s（范围 10–90） | 返回 HTTP 504 | REAL |
| `backend/api/agent.py` — 工具调用超时 | `_remaining_seconds(deadline, cap=5.0)` | 工具调用被截断，返回 error JSON | REAL |
| `backend/api/agent.py` — LLM 调用超时 | `_remaining_seconds(deadline)`，cap 30s | 抛出 `TimeoutError` → 504 | REAL |
| `src/api/routes/batch_missions.py` — SQLite 注册表连接 | `timeout=10` | `sqlite3.OperationalError` | REAL |
| `src/interrogator/daemon.py` — HTTP 信号源 | `timeout=25.0` | 请求失败，daemon 可能丢失信号 | REAL |
| `src/interrogator/probes.py` — 探测请求 | `timeout=20.0` | 探测失败，可能误报 | REAL |
| `backend/api/factory_strategy.py` — Campaign 任务预算 | `max_wall_seconds: 1800` | 任务超时后状态不确定 | REAL |

### 3.3 基线数据（待采集）

> **注意**：以下基线指标需从生产/测试环境实际采集，当前为占位符。

| 指标 | 当前值（待采集） | 采集方法 |
|---|---|---|
| 任务超时率（超时任务数 / 总任务数） | TBD | 查询 `tensor_dev_missions` 中 `status='failed'` 且 `result` 含 timeout 关键字的比例 |
| Agent 端 504 发生率 | TBD | 分析 API 访问日志中 `/agent/chat` 的 504 响应占比 |
| 批量提交超时率 | TBD | 分析 `/tensor/missions/batch` 的响应时间与 `atomic` vs `degraded_sequential` 模式分布 |
| 平均任务完成时间 | TBD | 查询 `tensor_dev_missions` 中 `succeeded` 任务的 `created_at` 到 `updated_at` 差值 |
| P95 任务完成时间 | TBD | 同上，取 95 分位 |
| 超时任务中可重试比例 | TBD | 分析超时任务的 `result` 字段，区分可重试（网络/上游）与不可重试（逻辑错误） |

### 3.4 根因假设（待验证）

1. **预算分配不合理**：Agent 总超时 45s 在 LLM 响应慢（>20s）+ 工具调用（5s × 3）场景下必然超时
2. **级联超时**：上游超时导致下游任务堆积，形成雪崩
3. **无超时预算继承**：子任务不继承父任务剩余时间预算，各自独立计时
4. **SQLite 注册表锁竞争**：批量提交时 SQLite 连接超时（10s）在高并发下触发
5. **状态机缺口**：超时后任务状态可能停留在 `claimed` 或 `running`，无自动回收机制

## 4. 可观测目标行为（Observable Target Behavior）

治理完成后，系统应表现出以下**可观测**行为变化：

### 4.1 超时定义标准化

| 超时类型 | 定义 | 可观测信号 |
|---|---|---|
| **Agent 端超时** | `/agent/chat` 返回 504 | HTTP 状态码 504 + `detail` 含「超时」 |
| **任务执行超时** | mission `status='failed'` 且 `result.error` 含 timeout | DB 查询 |
| **批量提交超时** | `/tensor/missions/batch` 响应时间 > 30s | API 延迟指标 |
| **探测超时** | interrogator probe 返回失败 | interrogator 日志 |

### 4.2 期望行为

1. **超时可区分**：每次超时事件都能被归类到上述四种类型之一
2. **超时可追溯**：每个超时事件关联到具体的 mission_id、agent_session_id、时间戳
3. **超时可告警**：超时率超过阈值时触发告警（Prometheus/Alertmanager）
4. **超时可恢复**：超时任务在合理时间内被自动回收或标记为可重试
5. **超时不扩散**：单个任务超时不导致其他任务连锁超时

## 5. 验收判据（Acceptance Criteria）

以下判据全部满足时，本变更契约视为验收通过：

### AC-1：超时率下降

| 判据 | 目标值 | 验证方法 |
|---|---|---|
| Agent 端 504 发生率 | ≤ 1%（按请求数计） | 分析 7 天 API 日志 |
| 任务执行超时率 | ≤ 3%（按任务数计） | 查询 `tensor_dev_missions` |
| 批量提交超时率 | ≤ 2%（按批次计） | 分析 batch API 日志 |

### AC-2：超时可观测性

| 判据 | 目标值 | 验证方法 |
|---|---|---|
| 超时事件分类覆盖率 | ≥ 95% 的超时事件可归类 | 抽样 100 个超时事件人工分类 |
| 超时事件可追溯率 | 100% 的超时事件可关联到 mission_id | 查询超时日志 |
| 告警触发准确率 | ≥ 90%（无误报/漏报） | 注入模拟超时事件验证 |

### AC-3：超时恢复能力

| 判据 | 目标值 | 验证方法 |
|---|---|---|
| 超时任务自动回收率 | ≥ 80% 的超时任务在 5 分钟内被回收 | 注入超时任务观察状态变化 |
| 可重试任务重试成功率 | ≥ 70% | 分析重试任务最终状态 |

### AC-4：回归验证

| 判据 | 目标值 | 验证方法 |
|---|---|---|
| 治理后 30 天内超时率不反弹 | 持续满足 AC-1 | 持续监控 |
| 治理不引入新超时点 | 新增超时点数量 = 0 | 代码审计 + 测试 |

---

## 6. 非目标（Non-Goals）

以下内容**明确排除**在本变更契约范围之外：

1. **不优化 LLM 本身响应速度**：LLM 响应慢是上游问题，本契约只治理超时预算分配与可观测性
2. **不改变任务状态机语义**：`queued → claimed → running → succeeded/failed` 的状态流转不变
3. **不引入新的消息队列中间件**：不引入 Redis/RabbitMQ/Kafka 等外部依赖
4. **不修改数据库 schema**：不新增表或列（除非作为独立变更提案）
5. **不处理非超时类失败**：逻辑错误、权限拒绝、数据校验失败等不在本契约范围
6. **不优化单次 LLM 调用的 token 消耗**：这是成本优化问题，非超时治理问题

## 7. 假设与未知（Assumptions & Unknowns）

### 7.1 假设

| # | 假设 | 验证方式 |
|---|---|---|
| A1 | 生产环境存在可查询的 API 访问日志 | 确认日志基础设施可用 |
| A2 | `tensor_dev_missions` 表包含足够的超时诊断信息（`result` 字段） | 抽样查询验证 |
| A3 | 超时主要由预算分配不合理引起，而非基础设施故障 | 分析超时事件分布 |
| A4 | 平台有 Prometheus/Alertmanager 或等效监控基础设施 | 确认监控栈可用 |
| A5 | 批量提交降级模式（`degraded_sequential`）是超时的主要来源之一 | 分析 batch API 日志 |

### 7.2 未知

| # | 未知项 | 影响 | 解决路径 |
|---|---|---|---|
| U1 | 当前实际超时率是多少 | 无法设定合理基线 | 先采集 7 天数据 |
| U2 | 超时事件的根因分布 | 无法确定治理优先级 | 对超时事件做根因分析 |
| U3 | 任务超时后是否有自动回收机制 | 影响 AC-3 的可行性 | 审查状态机与守护进程 |
| U4 | 批量提交在高并发下的实际表现 | 影响 AC-1 的批量提交指标 | 做负载测试 |
| U5 | Agent 超时与任务超时的关联程度 | 影响治理策略 | 关联分析两类超时事件 |

## 8. 风险（Risks）

| # | 风险 | 可能性 | 影响 | 缓解措施 |
|---|---|---|---|---|
| R1 | 基线数据采集不完整，导致目标设定不合理 | 中 | 高 | 先做 7 天数据采集，再设定目标 |
| R2 | 超时治理引入新的超时点（如监控采集超时） | 低 | 中 | 治理方案需经过超时影响评估 |
| R3 | 自动回收机制误回收正常运行的长任务 | 中 | 高 | 回收阈值需基于 P99 任务完成时间设定 |
| R4 | 告警阈值设置不当导致告警疲劳 | 中 | 中 | 告警阈值需基于基线数据动态调整 |
| R5 | 治理方案与现有状态机冲突 | 低 | 高 | 治理方案需通过状态机兼容性审查 |
| R6 | 批量提交原子性保证与超时治理冲突 | 低 | 中 | 需明确原子提交与超时恢复的优先级 |
