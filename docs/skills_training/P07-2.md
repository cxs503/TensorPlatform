最重要的一条方法论结论：**我第一版探针把「无鉴权」判定为 critical 缺陷，是错的。**
孤立挂载 router（`FastAPI().include_router(fu.router)`）绕过了 `backend/main.py:598` 的最外层 JWT 守卫，
得到"无凭据 POST /upload → 200"。把中间件按真实执行路径挂回后，同一请求变为 401。
这条负控（探针 A-00）被保留在结果里：**评审的"执行路径重建"若缺中间件栈，鉴权结论会整体反向。**

## 1. 方法与流程（先方法论，再证据）

### 1.1 五步法

1. **自拟契约（评审前冻结）**：先不读实现，按"这个端点应当保证什么"写出 `design_spec.md`（10 条 INV + 威胁模型 T1–T6 + 非功能 NFR-1..5）与 `test_plan.md`（26 条用例，含负例）。冻结后不再修改——避免以实现为中心的事后合理化。
2. **重建执行路径**：从 HTTP 入口回溯到磁盘/数据库落点，逐层记录中间件、依赖注入、写盘与 SQL 语句（见 §2）。
3. **探针化执行**：每条用例写成可复现探针（`probe_upload.py`），输出结构化观测（`probe_results.json`），不靠"读码推断"下判定。
4. **判定分级**：`CONFIRMED_DEFECT`（探针可复现）/ `ACCEPTED_RISK`（可复现但属设计取舍，登记）/ `OK`（符合契约）/ `UNTESTED`（未测风险，须写理由与补测成本）。
5. **严重度排序 + 处置**：S0–S3 判据见 §5，处置给到"改哪一行、加什么依赖"的粒度。

### 1.2 探针工程质量控制

- **不改生产代码**：`UPLOAD_DIR` 与 `MAX_FILE_SIZE` 仅在测试期替换为临时目录/缩放值（可逆），模块原样导入。
- **DB 独立**：`DATABASE_URL` 在 import 前注入为文件型 SQLite；表结构由 `011_file_upload.sql` **逐语句翻译后执行**，翻译率即 NFR-4 证据。
- **负控**：A-00（隔离挂载 vs 真实中间件栈）证明探针自身环境保真度不足会带来假缺陷；C-03 用依赖注入的 fake row 做后端无关复现，避免把"MySQL/SQLite 驱动差异"误当成逻辑缺陷。
- **异常不掩盖**：每条探针 try/except，异常本身写入 `evidence.traceback`。

## 2. 执行路径重建（真实调用链）

```
HTTP POST /upload  (multipart: file + category)
 └─ backend/main.py:598  jwt_auth_middleware = auth_guard_middleware   ← 最外层，验签+注入 request.state.current_user

 └─ backend/api/domain/tools.py:17,37  include_router(file_upload_router)（无前缀）
 └─ backend/api/file_upload.py:101 upload_file()
     ├─ :104  category: str = Form(default="general")      ← 客户端可控、无枚举校验
     ├─ :114  file_content = await file.read()             ← **整包读入内存**后才校验
     ├─ :116  validate_file(filename, len)                 ← 尺寸用 '>'、扩展名白名单
     ├─ :130  save_file()
     │    ├─ :76  unique_filename = uuid4.hex.ext          ← 落盘名与客户端文件名解耦（好）
     │    ├─ :79  category_dir = os.path.join(UPLOAD_DIR, category)   ← **无围栏，可逃逸**
     │    ├─ :84  open(file_path,"wb") + shutil.copyfileobj ← **非原子写入，无 .part+rename**
     │    └─ :88  os.path.getsize
     ├─ :143  INSERT INTO uploaded_files ... RETURNING id  ← 先落盘、后写库（顺序决定孤儿）
     ├─ :152  except → logger.warning，file_id=None        ← **库失败仍算成功**
     └─ :165  return {success: True, file_id, ...}
GET /files/{id}   → :311 SELECT * → :325 f[7].isoformat()          ← 按列序取 f[7]，实际是 mime_type
GET /files        → :303 except → {total:0, items:[]}              ← 故障伪装成空集
GET /download/{id}→ FileResponse（Range 正确：探针 R-04 得 206 + "2345"）
DELETE /files/{id}→ 先删物理文件、后删记录（探针 C-07：一致，重复删除 404）
```

**与 `011_file_upload.sql` 的结构错位**：表有 `uploaded_by / checksum / is_public / status / mime_type` 等 11 列，
实现只写 6 列（`filename, original_filename, category, file_path, file_size, extension`），
**`uploaded_by` 从不写入** → 存在"无主体归属"的数据模型空洞，直接导致文件级授权不可能实现（见 D-03）。

## 5. 严重度判据与排序结论

判据（先定后评，避免"感觉严重"）：

- **S0 阻断**：跨安全边界且**无需特殊条件**即可触发（越权读删、任意路径写）→ 发布前必修。
- **S1 高**：单一正常请求即可导致可用性/数据完整性损坏（OOM、孤儿文件、半成品、权限粒度缺失）。
- **S2 中**：契约违背但触发需附加条件，或主要影响可观测性/可维护性（字段错位、静默空集、无续传）。
- **S3 低**：卫生类（信息泄露细节、去重、种子行、迁移可移植）。

排序结论：**D-01/D-02/D-03 三条 S0 必须同批修**——它们共享同一根因族"客户端输入无条件进入存储层"（目录分量、主体归属）。
先修 D-03（授权）再修 D-01（围栏）会出现"合法用户可逃逸"；反之则"未授权者可越权"。
建议一次性把"输入 → 枚举/围栏"与"主体 → 权限"两条链路补齐，再进 D-04..D-08（可用性/一致性）。
