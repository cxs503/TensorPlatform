# P05-1: Experimental Design — Caching Strategy Comparison

## 1. Decision

**Question**: Which caching strategy should be adopted for a web service handling Zipf-distributed request traffic with temporal locality bursts?

**Competing Alternatives**:
- **Strategy A (LRU+Fixed-TTL)**: Least Recently Used eviction with a fixed 300-second time-to-live.
- **Strategy B (LFU+Adaptive-TTL)**: Least Frequently Used eviction with adaptive TTL scaling logarithmically with access frequency (60–600 seconds).

---

## 2. Hypothesis

**H₁**: LFU+Adaptive-TTL achieves a hit rate within ±3% of LRU+Fixed-TTL while reducing the stale data rate by ≥20%, without increasing P99 tail latency by more than 10%.

**H₀**: No meaningful difference exists between the two strategies on the stated metrics, or LFU+Adaptive-TTL fails one or more thresholds.

**Outcome Metrics**:
| Metric | Definition | Unit |
|---|---|---|
| Hit Rate | Fraction of requests served from cache | ratio [0,1] |
| Stale Rate | Fraction of cache hits serving data older than 120s | ratio [0,1] |
| P50 Latency | Median per-request latency | ms |
| P95 Latency | 95th percentile latency | ms |
| P99 Latency | 99th percentile latency | ms |
| P999 Latency | 99.9th percentile latency | ms |
| Mean Latency | Arithmetic mean latency | ms |

**Unit of Analysis**: Individual HTTP request.

**Target Workload**: Fixed synthetic trace of 50,000 requests over 2,000 unique keys, Zipf-distributed (α=1.2) with 15% temporal locality bursts, cache capacity 500 entries.

---

## 3. Baseline and Control

**Baseline**: LRU+Fixed-TTL (Strategy A) — the industry-standard approach, widely deployed, well-understood behavior.

**Control**: Both strategies run on the *identical* fixed request trace (SHA256 prefix `b4679346b10728c4`), with identical cache capacity (500), identical warmup period (first 5,000 requests excluded from metrics), and identical noise model for latency simulation. The only varied factor is the eviction policy and TTL mechanism.

---

## 4. Predeclared Thresholds and Stopping Rules

| Threshold | Value | Rationale |
|---|---|---|

| P99 latency increase | ≤ 10% | Tail latency degradation beyond 10% is user-perceptible |

| Warmup exclusion | First 5,000 requests | Allows cache to reach steady state before measurement |

**Exclusion criteria**: None applied (deterministic trace, no missing data).

**No post-hoc threshold tuning**: All thresholds declared before result inspection.

## 5. Confounders and Nuisance Variables

| Confounder | Control Method |
|---|---|
| Request order effects | Fixed trace, identical for both strategies |
| Latency measurement noise | Gaussian jitter with fixed seeds per repetition |
| Cache warm-up state | 5,000-request warmup excluded from all metrics |
| Temporal locality patterns | Embedded in trace generation; identical for both |
| Key popularity skew | Zipf α=1.2 fixed; same for both |
| Memory pressure | Identical capacity (500 entries) |
| Clock drift / time simulation | Single-threaded simulation, monotonic clock |
| Random seed effects | 5 repetitions with different noise seeds (SEED + k×1000 + 7) |

**Carry-over effects**: Not applicable — each repetition is independent (cache reset between runs).

**Selection bias**: Not applicable — trace is synthetically generated, not sampled from production.

**Measurement error**: Latency model is simplified (base + jitter); real systems would have GC pauses, network variability, etc. This is a *simulation-level* experiment, not production measurement.

---

## 6. Controlled and Changed Variables

| Variable | LRU+Fixed-TTL | LFU+Adaptive-TTL |
|---|---|---|
| Eviction policy | LRU (least recently accessed) | LFU (least frequently accessed) |
| TTL mechanism | Fixed 300s | Adaptive: 60s + log(1+count)/log(101) × 540s |
| Cache capacity | 500 | 500 |
| Freshness threshold | 120s | 120s |
| Trace | Identical (fixed) | Identical (fixed) |
| Noise model | Identical (same seeds) | Identical (same seeds) |

**Interaction consideration**: The adaptive TTL interacts with the LFU frequency counter — popular items get longer TTLs, which increases their chance of becoming stale. This is an inherent property of the design, not a confounder.

---

## 7. Repetition Rationale

**5 repetitions** were chosen because:
- The trace is fixed and deterministic; the only source of variance is the latency noise model.
- With low-variance metrics (σ ≈ 0.0003 for hit rate, σ ≈ 0.002 for stale rate), 5 repetitions yield a standard error of the mean ≈ σ/√5, sufficient to detect differences at the predeclared thresholds.
- Computational cost is modest (~2 seconds total), so more repetitions would not be prohibitive but are unnecessary given the low variance.

If variance had been higher (e.g., σ > 0.01 for hit rate), we would have increased to 20+ repetitions.

---

## 8. Randomization, Ordering, and Environment Controls

- **Randomization**: Noise seeds are deterministic (SEED + k×1000 + 7 for k=0..4), ensuring reproducibility.
- **Ordering**: LRU always runs before LFU in each repetition. Since the trace is fixed and caches are independent, ordering does not affect results. In a production A/B test, random assignment would be required.
- **Environment**: Single-threaded Python 3 simulation. No external dependencies beyond standard library + matplotlib (for figures). No network, no disk I/O during measurement.
- **Blinding**: Not applicable — the experimenter knows which strategy is which. In a production setting, blind evaluation would prevent bias.

### 12.3 Decision Analysis

| Criterion | Result | Threshold | Met? |
|---|---|---|---|
| Hit rate equivalent (Δ < 3%) | Δ = 1.96% | 3% | ✅ Yes |
| P99 acceptable (≤ +10%) | +0.2% | +10% | ✅ Yes |
| Stale improved (≥ 20% reduction) | −15.0% (LFU *worse*) | +20% | ❌ No |

**Decision**: **No clear winner.** LRU+Fixed-TTL and LFU+Adaptive-TTL have equivalent hit rates and nearly identical tail latencies. However, LFU+Adaptive-TTL has a *higher* stale rate (65.5% vs 57.0%), contrary to the hypothesis. The adaptive TTL mechanism, by giving popular items longer lifetimes, actually increases the probability that a hit serves stale data.

### 12.4 Interpretation

The key finding is that **adaptive TTL does not improve data freshness** under this workload. The mechanism works as follows:

1. LFU tracks access frequency, giving popular items higher counts.
2. The adaptive TTL formula maps higher counts to longer TTLs (up to 600s vs fixed 300s).
3. Longer TTLs mean items stay in cache longer, increasing the chance they exceed the 120s freshness threshold.
4. Since popular items are accessed more frequently, they accumulate more stale hits.

This is a fundamental trade-off: adaptive TTL optimizes for *retention* of popular items, not *freshness*. If freshness is the goal, a separate freshness-aware eviction policy (e.g., TTL-aware LRU, or explicit invalidation) would be needed.

## 13. Limitations and Scope

| Limitation | Impact |
|---|---|
| Simulated latency model | Real systems have GC pauses, network jitter, lock contention — not captured here |
| Single workload pattern | Only Zipf α=1.2 with 15% burst probability tested; results may differ for uniform or heavy-tail workloads |
| No write/invalidation traffic | Read-only workload; real caches handle writes, deletions, and explicit invalidations |
| Single cache size | Capacity=500; results may scale differently at larger capacities |
| No concurrent access | Single-threaded; real caches handle concurrent reads/writes with locking overhead |
| Simplified staleness model | Staleness is purely time-based; real systems may have version-based or event-based freshness |

**Scope of inference**: Results apply to read-only caching of time-sensitive data under Zipf-distributed access patterns. Do not extrapolate to write-heavy workloads, distributed caches, or systems with explicit invalidation.

## 15. Decision Supported

**Recommendation**: For this workload class (read-only, Zipf-distributed, time-sensitive data), **LRU+Fixed-TTL is preferred** over LFU+Adaptive-TTL because:

1. Hit rates are equivalent (within 3% threshold).
2. Tail latencies are equivalent (within 10% threshold).
3. LRU has a **15% lower stale rate** — meaning fresher data served to users.
4. LRU is simpler to implement and reason about.

If freshness is not a concern (e.g., static content caching), LFU+Adaptive-TTL may be worth considering for its slightly better retention of popular items — but this was not demonstrated in the current experiment.
