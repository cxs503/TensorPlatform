## Step 2 — Root Cause Analysis

### Invariant Violated
> **"Each mission_id shall have exactly one authoritative result write."**

### Assumption That Failed
The dispatcher assumed: *no heartbeat for 30 s ⇒ worker is dead*.  
Reality: network partition / GC pause / slow I/O can cause heartbeat gaps without worker death.

### Missing Guard
1. **No idempotency key** on result writes — any worker could overwrite `runs/{mission_id}/result.json`.
2. **No advisory lock** on mission execution — two workers could run the same mission concurrently.
3. **Retry logic did not check** whether the original worker had already completed before re-queuing.

### Mechanism (1 sentence)
The dispatcher's heartbeat-timeout retry path re-queued a mission that was still in-flight on the original worker, and the result-storage layer accepted writes from both workers without deduplication, causing a last-writer-wins race.

### Change 1: Dispatcher retry guard (`dispatcher.py`)

```python
# BEFORE (lines 142-155)
async def _handle_heartbeat_timeout(self, mission_id: int):
    mission = await self.repo.get_mission(mission_id)
    if mission.status == MissionStatus.RUNNING:
        logger.warning(f"Heartbeat timeout for mission {mission_id}, retrying")
        await self.repo.update_status(mission_id, MissionStatus.QUEUED)
        await self.queue.enqueue(mission_id)

# AFTER
async def _handle_heartbeat_timeout(self, mission_id: int):
    mission = await self.repo.get_mission(mission_id)
    if mission.status == MissionStatus.RUNNING:
        # NEW: check if worker actually completed (late heartbeat)
        if await self.result_store.has_result(mission_id):
            logger.info(f"Mission {mission_id} already has result, skipping retry")
            await self.repo.update_status(mission_id, MissionStatus.COMPLETED)
            return
        # NEW: advisory lock — only retry if lock is stale (>60s since heartbeat)
        lock_age = (utcnow() - mission.last_heartbeat_at).total_seconds()
        if lock_age < 60:
            logger.info(f"Mission {mission_id} lock age {lock_age:.0f}s < 60s, waiting")
            return
        logger.warning(f"Heartbeat timeout for mission {mission_id}, retrying")
        await self.repo.update_status(mission_id, MissionStatus.QUEUED)
        await self.queue.enqueue(mission_id, retry_count=mission.retry_count + 1)
```

### Change 2: Idempotent result write (`result_store.py`)

```python
# BEFORE
async def write_result(self, mission_id: int, result: dict):
    path = self.result_dir / f"{mission_id}" / "result.json"
    path.parent.mkdir(parents=True, exist_ok=True)
    path.write_text(json.dumps(result))

# AFTER
async def write_result(self, mission_id: int, result: dict, worker_id: str):
    path = self.result_dir / f"{mission_id}" / "result.json"
    meta_path = self.result_dir / f"{mission_id}" / ".write_meta.json"
    # Idempotency: first writer wins
    if path.exists():
        existing_meta = json.loads(meta_path.read_text())
        if existing_meta["worker_id"] != worker_id:
            raise DuplicateResultError(
                f"Mission {mission_id} already has result from "
                f"worker {existing_meta['worker_id']}, "
                f"rejecting write from {worker_id}"
            )
        return  # same worker re-writing = idempotent, allow
    path.parent.mkdir(parents=True, exist_ok=True)
    # Atomic write via temp file + rename
    tmp_path = path.with_suffix(".tmp")
    tmp_path.write_text(json.dumps(result))
    tmp_path.rename(path)
    meta_path.write_text(json.dumps({
        "worker_id": worker_id,
        "written_at": utcnow().isoformat()
    }))
```

## Step 4 — Regression Test

### Test: `tests/test_dispatcher/test_retry_idempotency.py`

```python
import pytest
from datetime import datetime, timedelta
from backend.services.dispatcher import Dispatcher
from backend.services.result_store import ResultStore, DuplicateResultError
from backend.models.mission import Mission, MissionStatus

@pytest.mark.asyncio
async def test_retry_does_not_duplicate_completed_mission(tmp_path):
    """
    Regression test for m5891 incident:
    When a worker completes a mission after heartbeat timeout but before retry,
    the retry must NOT re-queue the mission.
    """
    # Setup
    result_store = ResultStore(result_dir=tmp_path / "runs")
    dispatcher = Dispatcher(result_store=result_store, ...)
    
    # Create mission in RUNNING state
    mission = await dispatcher.repo.create_mission(
        mission_id=5891, action="resistance_calculation"
    )
    await dispatcher.repo.update_status(5891, MissionStatus.RUNNING)
    
    # Simulate: original worker writes result (late completion)
    await result_store.write_result(5891, {"Cb": 0.56}, worker_id="tp-gen-3")
    
    # Trigger heartbeat timeout handler
    await dispatcher._handle_heartbeat_timeout(5891)
    
    # Assert: mission stays COMPLETED, not re-queued
    updated = await dispatcher.repo.get_mission(5891)
    assert updated.status == MissionStatus.COMPLETED
    assert not await dispatcher.queue.contains(5891)

@pytest.mark.asyncio
async def test_result_store_rejects_duplicate_from_different_worker(tmp_path):
    """
    Second guard: even if two workers race, only the first write succeeds.
    """
    store = ResultStore(result_dir=tmp_path / "runs")
    
    # First worker writes successfully
    await store.write_result(5891, {"Cb": 0.56}, worker_id="tp-gen-3")
    
    # Second worker's write is rejected
    with pytest.raises(DuplicateResultError):
        await store.write_result(5891, {"Cb": 0.57}, worker_id="tp-gen-7")
    
    # Original result preserved
    result = await store.read_result(5891)
    assert result["Cb"] == 0.56

@pytest.mark.asyncio
async def test_result_store_allows_idempotent_rewrite_by_same_worker(tmp_path):
    """
    Same worker re-writing (e.g., after its own retry) is allowed — idempotent.
    """
    store = ResultStore(result_dir=tmp_path / "runs")
    
    await store.write_result(5891, {"Cb": 0.56}, worker_id="tp-gen-3")
    await store.write_result(5891, {"Cb": 0.56}, worker_id="tp-gen-3")  # no error
    
    result = await store.read_result(5891)
    assert result["Cb"] == 0.56
```

## Step 5 — Distillation (Runbook)

### Applicable Boundary
- **Service**: Mission dispatcher + result storage
- **Operation**: Any task with side-effects (file writes, DB mutations, external API calls)
- **Failure mode**: Heartbeat-timeout retry racing with slow-but-alive original worker
- **Not applicable**: Pure read-only queries; stateless computations with no shared output

### Source
- **Incident**: m5891 duplicate processing, 2026-11-05
- **Commit**: `a3f7c21` (dispatcher retry guard + idempotent result store)
- **Run ID**: `run_20261105_140211_m5891`

### Mechanism
The dispatcher's heartbeat-timeout retry path re-queued a mission that was still in-flight on the original worker (slow network, not crash). The result-storage layer accepted writes from both workers without deduplication, causing a last-writer-wins race that silently corrupted the output.

### Reusable Procedure

**Prevention** (design time):
1. Every side-effecting operation must have an **idempotency key** (e.g., `mission_id + worker_id`).
2. Result storage must enforce **first-writer-wins** semantics (or explicit overwrite protocol).
3. Retry logic must **check completion state** before re-queuing (not just heartbeat status).
4. Use **advisory locks** with stale-lock detection (lock age > 2× heartbeat timeout).

**Detection** (runtime):
1. Monitor for **multiple `COMPLETED` transitions** on the same mission_id.
2. Alert on **result file overwrites** (inode change, mtime regression).
3. Track **retry_count vs. completion_count** — if completion_count > 1, flag for review.

**Remediation** (post-incident):
1. Identify all missions with duplicate completions in the incident window.
2. For each, determine which result is authoritative (first writer, or re-run from scratch).
3. Invalidate downstream consumers that used the wrong result.
4. Backfill missing audit log entries.

### Counter-examples & Limitations

**When NOT to apply this runbook**:
- **Stateless, idempotent computations**: If the operation is truly idempotent (e.g., `GET /health`), duplicate execution is harmless. Don't add locks where they're not needed.
- **Explicit retry-with-overwrite protocols**: Some operations are designed to be re-runnable with newer data (e.g., cache refresh). First-writer-wins would break these.
- **Single-writer systems**: If only one worker can ever process a mission (e.g., partitioned queues with strict ownership), the race condition cannot occur.

**Known edge cases**:
- **Clock skew**: If worker clocks drift >30s, stale-lock detection may falsely flag live workers. Use NTP-synced clocks or logical timestamps.
- **Crash after write, before meta**: If a worker crashes between writing `result.json` and `.write_meta.json`, the result exists but meta doesn't. Recovery: treat missing meta as "no result" and allow overwrite.
- **Network partition during write**: Atomic rename protects against partial writes, but if the rename itself fails, cleanup is needed.

### Mechanical Guardrails

**Automated checks** (can be enforced in CI/CD or runtime):

1. **Lint rule**: Any function that writes to shared storage must accept an `idempotency_key` parameter.
   ```python
   # bad
   def write_result(mission_id, result): ...
   # good
   def write_result(mission_id, result, worker_id): ...
   ```

2. **Assertion in result store**: `assert not path.exists() or meta.worker_id == current_worker_id` before every write.

3. **Monitor**: Prometheus metric `mission_duplicate_completions_total{mission_id}` — alert if >0.

4. **Audit log check**: Nightly job scans for mission_ids with >1 `COMPLETED` transition in the last 24h.

5. **Integration test**: `test_retry_idempotency.py` (above) runs in CI on every PR touching `dispatcher.py` or `result_store.py`.
