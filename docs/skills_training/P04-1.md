## 3. Competitive Hypotheses (5 hypotheses across 4 layers)

### H1 — Database Connection Pool Exhaustion (L2: Data/Middleware)

**Mechanism**:  
The SQLAlchemy/connection pool has a fixed `pool_size` (e.g., 10). Under steady-state, all connections are in use. New worker tasks that need DB access must wait in a queue for a connection to be returned. The wait time adds directly to task completion time. If pool was previously lightly loaded and is now saturated (e.g., due to a slow query holding connections longer, or a new code path opening additional connections), the queuing delay appears as doubled completion time.

**Supporting Evidence (to seek)**:
- `pool_status()` or SQLAlchemy pool metrics showing `checked_out` ≈ `pool_size`
- Application logs showing `QueuePool` timeout warnings
- DB-side `pg_stat_activity` showing many idle-in-transaction connections

**Falsification Signal**:
- Pool utilization metrics show `checked_out` well below `pool_size` → H1 is false
- No connection wait events in application logs → H1 is false

**Predicted Observation (if H1 is true)**:
- Task latency distribution becomes **bimodal**: tasks that get a connection immediately complete in ~30s; tasks that wait for a connection complete in ~60s (30s work + 30s wait)
- P50 latency doubles but P5 may be unchanged
- DB query execution time itself is unchanged; only connection acquisition time increases

---

### H2 — Disk I/O Contention from Background Processes (L3: Infrastructure/OS)

**Mechanism**:  
Worker tasks perform file I/O (writing artifacts, reading input data, logging). A new or increased background process (log rotation, metrics export, artifact garbage collection, Docker layer operations) is competing for disk bandwidth. The I/O scheduler introduces latency for worker file operations, directly inflating task wall-clock time.

**Supporting Evidence (to seek)**:
- `iostat -x 1` showing high `%util` on the data volume
- `iotop` showing non-worker processes consuming significant I/O bandwidth
- `dstat` showing elevated `io wait` in CPU metrics

**Falsification Signal**:
- Disk utilization is <40% during the affected period → H2 is false
- No new background processes started correlating with the latency change → H2 weakened significantly

**Predicted Observation (if H2 is true)**:
- CPU `iowait` percentage increases from baseline (e.g., <2% → >15%)
- Worker CPU utilization appears lower (spending time blocked on I/O, not computing)
- Latency correlates with I/O burst patterns (not constant — sawtooth or periodic)

---

### H3 — Memory Pressure / Garbage Collection Pauses (L1: Application)

**Mechanism**:  
A memory leak or increased memory allocation pattern (e.g., caching large model responses, accumulating task result objects) causes the Python GC to run more frequently or for longer durations. Each GC pause stops the worker thread, adding directly to task completion time. If GC frequency doubles or pause duration doubles, overall task time doubles.

**Supporting Evidence (to seek)**:
- GC logs (`gc.get_stats()`, `gc.callbacks`) showing increased collection count or pause duration
- Memory usage trending upward over time (RSS growing between tasks)
- `tracemalloc` snapshots showing growing allocations in specific code paths

**Falsification Signal**:
- GC statistics show normal collection frequency and pause duration → H3 is false
- Memory usage is stable (no growth trend) → H3 is false

**Predicted Observation (if H3 is true)**:
- Task latency shows **periodic spikes** corresponding to GC events
- Memory usage shows sawtooth pattern with **increasing baseline** over hours/days
- Gen2 collections become more frequent
- Latency increase is not uniform — some tasks are fast (no GC during execution), others are very slow (GC during execution)

---

### H4 — External LLM/Model API Latency Increase (L4: External Dependencies)

**Mechanism**:  
Worker tasks call external LLM APIs (e.g., for evaluation, grading, report generation). If the external API's response time has increased (due to their load, model update, rate limiting, or network path change), the worker's wall-clock time increases proportionally. The worker is blocked waiting for the HTTP response.

**Supporting Evidence (to seek)**:
- HTTP client logs showing increased `time_to_first_byte` and `total_time` for external API calls
- External API's own status page showing degraded performance
- Network latency measurements (ping/traceroute) to the API endpoint showing increase

**Falsification Signal**:
- External API response times in logs are unchanged → H4 is false
- Only tasks that don't call external APIs are affected → H4 is false
- External API status page shows normal operation → H4 weakened

**Predicted Observation (if H4 is true)**:
- **Only tasks that call external APIs** show increased latency; pure-computation tasks are unaffected
- Latency increase is proportional to number of external API calls per task
- Network throughput is normal; only latency (not bandwidth) is affected
- The increase may be intermittent (correlating with external API load patterns)

---

### H5 — Docker/Container Resource Throttling (L3: Infrastructure/OS)

**Mechanism**:  
The container's CPU quota (`--cpus` or cgroup `cpu.cfs_quota_us`) was reduced, or the host became oversubscribed (other containers on the same host consuming more CPU). The worker process is CPU-throttled by the kernel cgroup scheduler, receiving less CPU time per wall-clock second. Tasks that previously took 30s of CPU time now take 60s of wall-clock time because they only get 50% of a CPU.

**Supporting Evidence (to seek)**:
- `docker stats` showing CPU% well below the container's allocated CPUs
- cgroup throttle metrics: `cat /sys/fs/cgroup/cpu/cpu.stat` showing `nr_throttled` and `throttled_time` increasing
- Host-level `top`/`htop` showing other containers consuming CPU

**Falsification Signal**:
- Container CPU quota is unchanged and CPU utilization is well within quota → H5 is false
- No `nr_throttled` events in cgroup stats → H5 is false

**Predicted Observation (if H5 is true)**:
- **All tasks** show proportional latency increase (not just some)
- Container CPU% appears low (e.g., 50% of 1 CPU = effectively 0.5 CPU)
- The increase is **uniform** across all task types (not task-specific)
- No change in memory, disk, or network metrics

## 5. Cheapest Distinguishing Observation

**The single cheapest observation that discriminates among all 5 hypotheses**:

This single observation immediately discriminates:

| If you see... | Then... |
|---------------|---------|
| CPU% is low (e.g., <50% of allocated) | → H5 (CPU throttling) is likely; check cgroup stats to confirm |
| CPU% is normal but MEM% is high/growing | → H3 (GC/memory) is likely; check GC logs next |
| CPU% and MEM% are both normal | → H5 and H3 are eliminated; look at network I/O (H4) or disk I/O (H2) or DB pool (H1) |

**Second cheapest follow-up** (if docker stats is inconclusive):  
Add a one-line timing wrapper around the worker task that logs `(db_connect_time, compute_time, io_time, external_api_time)` — this single instrumentation point discriminates H1/H2/H4 in one observation by attributing time to each subsystem.

**Why this is cheapest**:
- `docker stats` requires zero code changes, zero new instrumentation
- It runs in <1 second
- It eliminates or promotes 2-3 hypotheses in one shot
- It's available on any Docker-based deployment without modification
