# P04-2: Backend Worker Completion Time Doubled — Diagnostic Analysis

**Training Objective**: Diagnose why a backend worker's completion time doubled while request volume remained constant. Provide ≥3 competitive explanations spanning ≥2 system layers with mechanism, evidence, falsification signals, and predictive observations. Identify the cheapest distinguishing observation.

**Discipline**: [SKILL_OFF] — Independent analysis without platform skill library.

---

## 1. Problem Statement

**Symptom**: Backend worker completion time increased from baseline T to 2T (100% increase).

**Constraint**: Request volume (requests/second) remained constant — ruling out simple load-based queueing.

**System Context**: FastAPI-based backend with PostgreSQL database, running in Docker containers, potentially with background task queues (Celery/RQ/asyncio workers).

---

## 2. Competitive Explanations (5 hypotheses across 3 system layers)

### Hypothesis 1: Database Connection Pool Exhaustion (Data Layer)

**Mechanism**:
- SQLAlchemy connection pool reached max size (default pool_size=5, max_overflow=10)
- New requests block waiting for available connections instead of executing immediately
- Each request now waits avg(T_wait) before execution, where T_wait ≈ T_execution
- Total time = T_wait + T_execution ≈ 2 × T_execution

**Supporting Evidence**:
- `backend/database/config.py` shows SQLAlchemy pool configuration
- Connection pool metrics would show `checked_out` connections at capacity
- PostgreSQL `pg_stat_activity` would show many idle-in-transaction connections
- Application logs may show "QueuePool overflow" warnings

**Falsification Signal**:
- If connection pool metrics show <50% utilization during slow period → FALSE
- If PostgreSQL shows no connection wait events → FALSE
- If adding `pool_pre_ping=True` doesn't change behavior → likely FALSE

**Predictive Observation**:
- Increasing `max_overflow` from 10 to 50 should reduce completion time by ~50%
- Connection wait time histogram should show bimodal distribution (fast path vs queued path)
- `SELECT count(*) FROM pg_stat_activity WHERE state = 'idle in transaction'` should be high

**System Layer**: Data/Infrastructure

---

### Hypothesis 2: Garbage Collection Pressure (Application Layer)

**Mechanism**:
- Memory leak or accumulation caused frequent major GC cycles
- Python's cyclic GC pauses application threads for 100ms-2s during collection
- Worker threads blocked during GC, increasing effective completion time
- Constant request volume means steady memory allocation rate → steady GC frequency

**Supporting Evidence**:
- Python `gc.get_stats()` would show increased collection counts
- Memory usage trending upward over time (RSS growth)
- `tracemalloc` snapshots show growing allocations
- Application logs may show GC-related delays

**Falsification Signal**:
- If `gc.get_stats()` shows stable collection frequency → FALSE
- If memory usage is flat (no leak) → FALSE
- If disabling GC (`gc.disable()`) doesn't improve performance → FALSE

**Predictive Observation**:
- Memory profiling should show linear growth pattern
- GC pause duration correlates with completion time spikes
- Setting `gc.set_threshold()` to higher values reduces frequency but increases pause duration
- Restarting the worker temporarily restores baseline performance

**System Layer**: Application/Runtime

---

### Hypothesis 3: Disk I/O Contention (Infrastructure Layer)

**Mechanism**:
- Background process (logging, metrics export, temp file cleanup) competing for disk I/O
- Worker performs synchronous file writes (logs, artifacts, model checkpoints)
- I/O wait time increased from <10ms to >500ms per operation
- Constant request volume means constant I/O demand → sustained contention

**Supporting Evidence**:
- `iostat` shows high `%util` (>80%) on data volume
- `iotop` reveals background processes with high I/O wait
- Application logs show slow file write operations
- Docker volume mount options may be suboptimal (no `async`, no `noatime`)

**Falsification Signal**:
- If `iostat` shows <30% disk utilization → FALSE
- If moving logs to tmpfs doesn't improve performance → FALSE
- If `strace -e trace=write` shows fast write syscalls → FALSE

**Predictive Observation**:
- `iostat -x 1` during slow period shows high await times (>100ms)
- Correlation between log write frequency and completion time
- Moving log directory to tmpfs reduces completion time by ~30%
- `hdparm -t /dev/sdX` shows degraded sequential read speed

**System Layer**: Infrastructure/OS

---

### Hypothesis 4: Network Latency to External Service (Network Layer)

**Mechanism**:
- Worker makes synchronous HTTP calls to external API (MLflow, HuggingFace, model registry)
- External service degraded (increased latency from 50ms to 500ms)
- Each request now waits for external call completion
- Constant request volume means constant external call rate → sustained latency impact

**Supporting Evidence**:
- `backend/main.py` shows `HF_ENDPOINT` and `MLFLOW` configuration
- Application logs show slow HTTP request durations
- `curl` to external endpoints shows increased latency
- Network monitoring shows packet retransmissions or high RTT

**Falsification Signal**:
- If external API response times are stable (<100ms) → FALSE
- If worker doesn't make external calls during request processing → FALSE
- If adding request timeout doesn't change behavior → FALSE

**Predictive Observation**:
- HTTP client metrics show p95 latency increased from 50ms to 500ms
- Correlation between external call duration and completion time
- Adding circuit breaker or caching reduces completion time
- `tcpdump` shows increased TCP retransmission rate

**System Layer**: Network/External Dependencies

---

### Hypothesis 5: CPU Throttling in Container (Infrastructure Layer)

**Mechanism**:
- Docker container CPU limit too restrictive (e.g., `--cpus=0.5` on multi-core workload)
- Worker threads throttled by cgroup CPU scheduler
- Effective CPU time reduced by 50%, doubling wall-clock completion time
- Constant request volume means constant CPU demand → sustained throttling

**Supporting Evidence**:
- `docker stats` shows CPU usage at limit (e.g., 50% on 1-core limit)
- `/sys/fs/cgroup/cpu/cpu.stat` shows `nr_throttled` increasing
- `perf` shows high context switch rate
- Application is CPU-bound (profiling shows compute-heavy functions)

**Falsification Signal**:
- If `docker stats` shows CPU <50% of limit → FALSE
- If `nr_throttled` is stable (no throttling events) → FALSE
- If increasing CPU limit doesn't improve performance → FALSE

**Predictive Observation**:
- `docker stats` shows CPU% consistently at limit (e.g., 49-50% on 0.5 core limit)
- `/sys/fs/cgroup/cpu/cpu.stat` shows `nr_throttled` incrementing rapidly
- Increasing `--cpus` from 0.5 to 2.0 reduces completion time by ~60%
- CPU profiling shows hot functions taking 2× expected time

**System Layer**: Infrastructure/Container Runtime

## 3. Cheapest Distinguishing Observation

**Recommended First Check**: **Database connection pool metrics + PostgreSQL activity**

**Rationale**:
1. **Low cost**: Single SQL query + application metrics endpoint
   ```sql
   SELECT state, count(*) FROM pg_stat_activity GROUP BY state;
   SELECT count(*) FROM pg_stat_activity WHERE wait_event_type = 'Lock';
   ```
2. **High discriminative power**: 
   - If `idle in transaction` > 10 → Hypothesis 1 likely
   - If no connection waits → Hypothesis 1 ruled out
3. **Fast**: <1 second to execute
4. **Non-invasive**: Read-only queries, no service disruption

**Decision Tree**:
```
Check pg_stat_activity
├─ High "idle in transaction" → Hypothesis 1 (DB pool)
├─ No connection waits → Rule out Hypothesis 1
│  └─ Check docker stats
│     ├─ CPU at limit → Hypothesis 5 (CPU throttling)
│     ├─ CPU < 50% → Rule out Hypothesis 5
│     │  └─ Check iostat
│     │     ├─ Disk %util > 80% → Hypothesis 3 (Disk I/O)
│     │     └─ Disk %util < 30% → Rule out Hypothesis 3
│     │        └─ Check external API latency
│     │           ├─ p95 > 500ms → Hypothesis 4 (Network)
│     │           └─ p95 < 100ms → Rule out Hypothesis 4
│     │              └─ Hypothesis 2 (GC pressure) most likely
```

**Alternative cheap checks** (if DB access unavailable):
1. `docker stats` — 1 command, rules in/out Hypothesis 5
2. `top` + `gc.get_stats()` — rules in/out Hypothesis 2
3. `iostat -x 1 5` — rules in/out Hypothesis 3

## 4. Evidence Collection Protocol

**Before collecting evidence, do NOT assume root cause.** Follow this protocol:

### Phase 1: Non-invasive observation (5 minutes)
1. Collect baseline metrics:
   - `docker stats --no-stream` (CPU, memory, network I/O)
   - `pg_stat_activity` snapshot (connection states)
   - `iostat -x 1 10` (disk utilization)
   - Application metrics endpoint (request latency histogram)
   - `gc.get_stats()` (GC frequency)

2. Correlate with completion time:
   - Plot completion time vs each metric over 10-minute window
   - Identify which metric correlates with slowdown

### Phase 2: Targeted hypothesis testing (15 minutes)
Based on Phase 1, test the top 2 hypotheses:

**If Hypothesis 1 (DB pool)**:
- Increase `max_overflow` to 50, measure completion time
- Expected: 30-50% improvement if correct

**If Hypothesis 2 (GC)**:
- Set `gc.set_threshold(100000, 10, 10)` (reduce frequency), measure
- Expected: Fewer spikes, but higher memory usage

**If Hypothesis 3 (Disk I/O)**:
- Move log directory to tmpfs, measure
- Expected: 20-30% improvement if correct

**If Hypothesis 4 (Network)**:
- Add request timeout (5s) + circuit breaker, measure
- Expected: Reduced tail latency if correct

**If Hypothesis 5 (CPU throttling)**:
- Increase `--cpus` from 0.5 to 2.0, measure
- Expected: 50-70% improvement if correct

### Phase 3: Confirmation (10 minutes)
- Run A/B test: baseline config vs modified config
- Measure completion time distribution (p50, p95, p99)
- Confirm improvement is statistically significant (>20% reduction, p<0.05)

## 5. Anti-Patterns to Avoid

**DO NOT**:
1. **Jump to conclusions**: "It's probably the database" without evidence
2. **Propose fixes before diagnosis**: "Let's add Redis caching" (solution before problem)
3. **Ignore constant request volume constraint**: This rules out simple load-based explanations
4. **Assume single root cause**: Multiple factors may contribute (e.g., DB pool + GC)
5. **Trust self-reported metrics**: Application logs may lie; use OS-level metrics (iostat, perf)
6. **Make invasive changes first**: Start with read-only observations before config changes

**DO**:
1. **Collect evidence before hypothesis**: Let data guide diagnosis
2. **Test multiple hypotheses in parallel**: Use decision tree to rule out efficiently
3. **Quantify improvement**: "30% faster" not "feels faster"
4. **Document falsification**: Record which hypotheses were ruled out and why
5. **Use cheapest tests first**: `pg_stat_activity` before full profiling

## 7. Verification Criteria

**Success = Correct diagnosis, not just performance improvement.**

To verify the diagnosis:
1. **Mechanism confirmed**: Direct evidence (e.g., `pg_stat_activity` shows connection waits)
2. **Falsification signals absent**: No contradictory evidence
3. **Predictive observation confirmed**: Expected behavior matches actual behavior
4. **Improvement quantified**: Measurable reduction in completion time after targeted fix
5. **No regression**: Other metrics (throughput, error rate) remain stable

**Failure modes**:
- Performance improved but root cause unknown (lucky config change)
- Multiple hypotheses partially correct (need to identify dominant factor)
- Diagnosis correct but fix insufficient (need to address secondary factors)
