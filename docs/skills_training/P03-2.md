# P03-2 调查：一个排队操作返回 HTTP 202，但用户报告永不完成

> 范围：TensorPlatform 后端真实代码（`/root/tp-agent/work/m6343`，分支 `agent/m6343`）+ 平台库只读快照。
> 本单**不改任何代码**（无 `src/`、`backend/`、`migrations/` 改动）；产物只落在 `docs/skills_training/`。
> 快照时间：2026-11-07 约 22:00 UTC（见 `docs/skills_training/P03-2/db_snapshot.txt`、`status_counts.txt`）。

---

## 0. 结论先行（TL;DR）

| 问题 | 判定 | 依据 |
|---|---|---|
| 用户报告的「HTTP 202」在本仓是否存在 | **否 — 已证实不存在** | 全仓 `status_code=202` / `HTTP_202_ACCEPTED` / `JSONResponse(status_code=202)` 零命中；受理端点走默认 200 |
| 「排队操作永不完成」是否存在 | **是 — 已证实存在，可复算** | 生产表 `tensor_dev_missions` 中 53 张 `status='queued'`，最老 12.1 h；其中 **45 张被 model 引脚钉死 11.1 h**，**6 张被 runner 归属钉死 12.1 h** |
| 「永不完成」的根因层级 | **不是 HTTP 层，是受理→消费之间的可认领性保证缺失** | 认领 SQL 是等值过滤的合取式、无旁路、无超期回收；只有 `claimed/running` 会被 lazy reap，`queued` 永不超期 |

一句话：**「202」是用户对异步受理契约的口语化描述；真实契约是「同步 200 + `{"status":"queued"}`」。症状为真，锅不在状态码，在于「受理时承诺了会完成，但没有任何机制保证队列项一定存在能领走它的消费者」。**

## 1. 案例介绍：被调查的操作与契约

被调查的「排队操作」是平台**唯一的主力工作队列**：开发任务（dev mission）队列。

| 项 | 值 |
|---|---|
| 消费者 | 常驻 agent daemon（`ops/tp_worker.py`，本机实测 20 个进程） |
| 队列载体 | PostgreSQL 表 `tensor_dev_missions`（`status` 列做状态机） |
| 状态词表（单一契约源） | `backend/contracts/mission_status_vocab.v1.json` v3 |
| 终态集合 | `succeeded / failed / stopped / revoked / orphan`（`terminal` 字段） |
| 非终态 | `queued / claimed / running / awaiting_acceptance / awaiting_pr_merge / suspended / reopened` |
| 受理 HTTP 码 | **200**（`return {"id":…, "status":"queued", …}`），无 `Location` / `Retry-After` 头 |
| 关联次队列 | 场景执行队列 `tensor_executions`（同型协议，消费者 `tools/executor/tensor_executor.py`） |

### 1.1 HTTP 层事实核查（「202」到底在哪）

| 检查 | 命令 | 结果 |
|---|---|---|
| 优雅码 `202` | `grep -rn "status_code=202\|status_code = 202\|JSONResponse(status_code=202\|202_ACCEPTED" --include=*.py .` | **0 命中** |
| 受理端点显式码 | `grep -n "@router.post" backend/api/tensor_missions.py` | 受理 `POST ""`（:133）无 `status_code=` 参数 → FastAPI 默认 **200** |
| 返回体语义 | `backend/api/tensor_missions.py:189` | `{"id", "session_id", "status":"queued", "budget"}` |
| 前端/网关是否改写为 202 | `grep -rn "202" frontend-console/src api/ harness_gateway/` | 无 202 语义命中 |

**判读**：报告里的「202」无法在本仓复现为字面状态码。可复现的是「**Accepted 语义**」：请求返回时任务尚未终态，客户端必须轮询 `GET /tensor/missions/{id}`。因此后续调查以「Accepted 语义」为对象，而不是以状态码为对象。（这一点很重要：如果照字面去查 202，会得出「不是我们的问题」的错误结论。）

## 2. 怎么做的（方法/流程/工具链）

1. **定位受理端点**：从「排队」语义出发，枚举全仓 `status='queued'` 的写点 → 收敛到 `tensor_missions`（主队列）与 `tensor_executions`（次队列）两条同构协议。
2. **逐跳读码**：受理 → 领取 → 执行 → 终态落库，每跳取 `file:line`，画出执行路径图（§3）。
3. **反证 HTTP 层**：全仓状态码 grep（§1.1），排除「202 被误用」假设。
4. **把「永不完成」变成机器可裁判据**：对「受理后未能终态」逐条写出可 SQL 化的条件（§5 表 A）。
5. **生产只读快照**：`psql -U postgres -d tensorplatform`（只读 SELECT）统计状态分布、各车道排队量与最老年龄、心跳陈旧度；`ps -ef` 抓在跑的 daemon 型号；两者交叉得到「车道死活」结论。原始输出落 `docs/skills_training/P03-2/`。
6. **测试边界盘点**：定位覆盖该路径的测试文件，逐条记录断言停在哪一跳（§6）。
7. **三分类**：已证实 / 推断 / 未知（§7），未证实项显式标注为推断或未知，不合并。

工具链：`grep` / `sed` 读码；`psql` 只读；`ps -ef`；`python3 + matplotlib` 出图（§4 图 1 由 SQL 结果程序化注入）。

### 3.2 领取 SQL 的过滤器（关键：合取式、无旁路）

`backend/api/tensor_missions.py:571-611`（读码复原）：

```
WHERE organization_id=:org AND status='queued' AND suspended_at IS NULL
  [AND runner = :runner]                       -- 传了就等值，不传则不限
  [AND (model = :claim_model [OR model IS NULL])]  -- 传了 model 就等值；claim_null_model 才放宽 NULL
  [AND id = :claim_mission_id]
  [AND worker_role = :worker_role] 或 AND worker_role IS NULL   -- ★不传则只领「无角色」单
  [AND agent_session_id = :sess]   或 AND agent_session_id IS NULL -- ★不传则只领「未指派」单
  AND NOT EXISTS (未终态依赖)          -- 依赖 pending 的 prerequisite 挡住
ORDER BY id LIMIT 1 FOR UPDATE SKIP LOCKED
```

结论：**引脚（model / runner / worker_role / agent_session_id）是「只有匹配者能领」的强约束，除此之外没有任何兜底**。一个被钉在 `model='glm-5.1'` 的 queued 单，其唯一可能的消费者是「发 `model='glm-5.1'` 的 daemon」；该 daemon 不存在 = 该单永久 queued。

## 5. 「永不完成」的机器可裁条件（判据先于修复）

| # | 判据（可 SQL 化） | 本快照是否成立 | 层级 |
|---|---|---|---|
| J1 | `status='queued'` 且 `now()-created_at > T`（T 取 240 min，沿用平台既有阈值） | **成立**（45 张 11.11 h、6 张 12.07 h） | 症状 |
| J2 | J1 的单，其「车道」近 6 h 无任何 claim 证据（`claimed_by`/`heartbeat_at`） | **成立**（glm-5.1：0；openhands：无该 runner 进程） | 根因 |
| J3 | 不存在任何**超期回收**路径把 `queued` 变终态：全仓无 `WHERE status='queued' AND created_at < ...` 的 fail/expire 写入 | **成立**（reap 只写 `claimed/running`；`/missions/{id}/stop` 需人工） | 机制缺口 |
| J4 | `complete(acceptance=true)` → `awaiting_acceptance` 为非终态，需 ADMIN 决策才能终态 | 结构成立（本时点 0 张，无存量证据） | 机制缺口 |
| J5 | `awaiting_pr_merge` 需外部 governor/PR 合并才终态 | 本时点 1 张、24 min（未超期） | 机制缺口 |

**结论**：J2 与 J3 同时成立 ⇒ 「受理即承诺完成，但完成依赖一个可能不存在的消费者，且系统不自检」——这是本症状的最小根因表述。

## 7. 三分类

### 7.1 已证实（可直接复算 / 读码可证）

1. 本仓**不存在** HTTP 202 的受理端点；受理是 200 + `{"status":"queued"}`（`tensor_missions.py:189`）。
2. 领取 SQL 为合取等值过滤，`model` / `runner` / `worker_role` / `agent_session_id` 四个引脚**无兜底分支**（:571-585）。
3. lazy reap 只处理 `claimed/running`（:541-550），**对 `queued` 无超期处理**。
4. 生产 53 张 queued 中，45 张钉在 `model='glm-5.1'`（最老 11.11 h），6 张 `runner='openhands'`（最老 12.07 h）。
5. 在跑的 20 个 `tp_worker` 进程无一个 `--model glm-5.1`；glm-5.1 车道近 6 h claim 计数 = 0；其最后终态完成于 2026-11-01 04:36。
6. `complete(acceptance=true)` 把单子留在 `awaiting_acceptance`（非终态），终态需 ADMIN `decide`（`tensor_approvals.py:229-250`）。
7. 「孤儿引脚」的判据与修复建议（解钉为 `model=NULL`）在 `backend/api/queue_adoption.py` 已有纯逻辑实现；`heal_plan` 无调度挂载。

### 7.2 推断（有代码/数据支撑，但未用实验闭环）

1. 用户口中的「202」= 对 Accepted 语义的口语化（或来自其他客户端/旧版/前端封装），非本仓字面契约；**无法排除**是第三方网关把 200 改写成 202。
2. 45 张 glm-5.1 单若被解钉为 `model=NULL`，会立即进入任一 native daemon 的公共池车道（由 attempt #4 的 `claim_null_model` 匹配）——**推断**，未实跑验证（本单不改代码、不动生产）。
3. `docs` 内前案（`queue_adoption.py` 文档头，2026-11-07）所述「注册 glm-5.1 的驻留会话只心跳、实际呈递别的 model」正是当前 `ps -ef` 中 `tp-gen-4 --model deepseek-v4-flash` 的现象；两者**同源**——但注册表 `factory_resident_workers` 与会话映射本轮未逐行核对，故列为推断而非证实。
4. 依赖门（`NOT EXISTS` 未终态依赖）会让「依赖一张永不终态的单」的下游单一起卡住；本快照未见该形态（53 张中无依赖阻塞），故属于**结构性风险而非当前主因**。

### 7.3 未知（证据不足）

1. 用户的具体受理请求（端点、时间、`mission_id`）未提供，无法把症状钉到某一张单上；本报告用「同类形态」替代单点复现。
2. `awaiting_acceptance` 的存量卡滞时长（本时点 0 张，历史分布未查）。
3. 是否存在其它平台实例（多节点）在跑 glm-5.1 daemon —— 本机 `ps` 只见本机 20 个进程；跨节点未证。

## 8. 图与误差判定

- **无场量云图**：本单是后端队列路径调查，不存在物理场量；可量化对象是「队列长度/年龄/状态」等离散计数，已用柱状漏斗图呈现（图 1），不存在网格场。
- **基准与误差**：本单**没有实验/解析/文献基准量**（不是数值仿真任务），因此「<3% 误差」判据**不适用**，不做事后编造的百分比。替代判据是**可复算性**：报告中每个数字都附了 SQL，任何人可在同一快照上复算；计数类量为精确整数，无舍入误差。唯一带阈值的是「240 min 超期」——该阈值沿用平台既有 `THRESHOLD_MINUTES=240`（`backend/api/queue_adoption.py`），不是本报告引入；实测最老排队 725 min（12.07 h）≈ 阈值的 3.0 倍，判定对阈值不敏感（阈值取 60 min 或 480 min 结论均不变）。

## 9. 注意点（坑 / 局限 / 适用范围）

1. **别看状态码看语义**：先按「202」grep 会得到 0 命中，容易误判「用户报错不存在」。异步契约的口语化描述必须翻译成「受理后是否保证终态」。
2. **心跳是掩盖洞的信号**：驻留会话心跳新鲜 ≠ 车道活着；判活必须看**近期 claim 证据**（前案文档原话，本轮 `ps` + SQL 复现）。
3. **`claimed is False` 不等于健康**：协议把「空闲」和「无匹配消费者」压成同一个返回体（:614），客户端与测试都看不出差别——这是可观测性缺口。
4. **reap 的语义是「保活」不是「保证」**：它只回收已领走的单，对「没人愿意领」的单没有语义。
5. **局限**：①单快照（约 22:00 UTC），未做时间序列；②只读，不改代码也不动生产，故「解钉即通」为推断；③三节点集群/其它宿主机上的 daemon 未核；④`factory_resident_workers` 注册表与会话映射未逐行比对。
6. **适用范围**：结论适用于 `tensor_missions` 与同构的 `tensor_executions`（后者心跳 reap 阈值 90 s，`backend/api/tensor_executions.py:271-284`；其消费者 `tools/executor/tensor_executor.py:553` 无服务化挂载，属同类风险面）。
