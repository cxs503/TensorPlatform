## ⑤ 注意点（踩坑/局限/适用范围）

1. **`verify` 对凭证环境敏感（本单最重要发现）**：shipped 台账 `relational_store` 记为 REAL（`psycopg round-trip via dotenv:.env`），但在当前树（无 `.env`、`TP_PG_DB` 有值而无 `TP_PG_USER/PASSWORD`）复跑落 **WITHHELD**：`dsn_candidates` 先取 env 候选，driver 与 psql 两条路都失败。`cli verify` 依约报 `VERIFY MISMATCH`（退出码 1）。因此「`verify` OK」是环境相关的可复算，而非无条件可复算——**KPI 不受影响（9 ≥ 5），但 L4 的「可复现」被这条打折**。
2. **3/10 类不变式近乎恒真**：`version_control`（head_sha_len=40、commit_count≥1）、`plotting_engine`（PNG 魔数+≥1000 B）、`relational_store`（`SELECT 6*7`）——它们证明「工具真跑了」，但不构成对计算正确性的外部锚定；`hdf5_store` 的往返是自洽而非外部真值。真正带外部锚的强判据只有 symbolic/quadrature/optimization/autodiff/gcc-H₁₀ 五类，**恰好等于 KPI 下界 5**。
3. **报告 ④ 表的措辞**：symbolic FD 行 got 写「9.0e-9 量级（见台账）」而台账实为 1.12e-9；列语义（ref/got）在该行混淆。数值仍在容差内，属表述精度问题。
4. **敏感性如实降级**：`sensitivity.json` 的 `all_within_limit=false`（80 trials 两 seed 均超 1e-3），规格 notes 明说「1e-3 是 200-trial 的 claim」——诚实，且是本单写得最好的一处纪律。
5. **记账缺口**：`tensor_dev_missions.report_id` 为 NULL（报告 14265 存在但未回链）、报告 `qa_status=pending`；不在本单判级上扣分，属平台侧记账待补。
6. **CLI 参数顺序**：`--out-dir/--repo` 是全局参数，必须写在子命令前（`cli --out-dir X run`）；文档中的复现命令用默认值，未踩到这个坑，但对外复用时会踩。
7. **未做（如实）**：未在集群节点（loong64 同架构）侧复跑；未对 10 个工具类逐一做版本矩阵（仅当前环境版本）；未做 API 端点并发/权限面压测。
