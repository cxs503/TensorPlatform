## 1. 归类口径（L0-L5 阶梯 + 两个统计层）

L0-L5 的判据键直接沿用审计波 `gate_note.why` 的机器判据（`tests` / `impl_files,entry,run_artifacts` / `integration_callers` / `benchmark`），因此本文档的分档与审计波同源、可对账：

| 档 | 名称 | 判据（必须同时满足） | Tier-B 机器信号 |
|---|---|---|---|
| L0 | 文档成果 | 有文档/图表/清单，无可执行实现 | changed_files 中无代码扩展名 |
| L1 | 数学验证成果 | 有测试/验证脚本，无独立功能实现 | 代码文件仅 `test_*`/`verify_*`/`audit_*` |
| L2 | 独立功能成果 | 实现文件 + 工程入口 + 可运行工件（入库） | 实现文件 **且** `result.pr_gate.state='merged'` |
| L3 | 集成成果 | L2 + 被集成面调用（跨仓或 api/backend/cli 集成面） | `co_repos≥2` 或改动命中集成面标记 |
| L4 | 基准验证成果 | L2/L3 + 与解析解/文献/实验对标且留 run 工件 | goal 命中基准词 **且** 有 runs/artifacts 图件 |
| L5 | 创造性成果 | 无先例的新方法 | **不可由文件信号机器判定**，只接受人工/审计判定 |

两个统计层必须分开读，混读就是造假的起点：

- **Tier-A 判定层**：`tensor_maturity_verdicts` 184 条 scope 级审计判定，每条带 claim level 与机器门实测 `gate_level`（判工件在审计工作树内是否真的可见可跑）。这是**实测**，样本小但硬。
- **Tier-B 代理层**：对全部 succeeded 任务按 changed_files / pr_gate / goal 做机器分档。覆盖全库但只是**信号代理**，精度由 §5 的验证集给出（18 对，exact 4，±1 8）。
- **严格 vs 宽松**：严格口径要求 PR 合并证据（owner 口径：没入库不算成果）；宽松口径只要求实现文件存在，用来量化「未入库的实现」有多大。差 = 膨胀的第一层来源。

**诚实声明（不许含糊）**：

1. Tier-A 的「gate≥L2 = 0」是**实测下界，不是全能力为零**。184 条里有 72 条因「工件缺失」在审计工作树内看不见文件（`gate_note.why` 命中「工件缺失」），这部分是**度量缺口**，须由协调者重开补齐工件后再判——所以 §3.1 才只列名单不改状态。
2. Tier-B 是**信号代理**，验证集只有 18 对（带 `(m####)` 的 audit scope），exact 4、±1 8，且偏差方向是代理高估。因此 §2.1 的六类分布只能读**相对量与趋势**，不能当绝对值引用。
3. 「报告 : 可运行算例」的分母用「带 run 工件的成功单」是代理信号（601 单），若改以审计实跑 5 条为分母，比值放大到 1832.6 : 1——两种口径都写在表里，读者可自选，但不许混用。
4. 本次统计**未做**的事：未重跑任何被审计能力项、未改任何任务状态、未按 PR 号去 GitHub 逐条核对。
5. **快照语义**：本文数字取自 `2026-11-11T09:33:54.755991+00:00` 那一刻的活库；平台每几分钟就新增任务，复跑会有小幅漂移（本次连续两次跑之间 total 已差 3 单）。同一快照内的自洽性由 `tests/test_restat_real_outputs.py` 的 12 条断言锁定（档位合计=成功单数、crosstab 行和=claim 分布、待完成名单条数=claim L0+L1 等），口径漂移会立刻红。

- `psycopg2` 在本沙箱是 stub（`RuntimeError: no real driver`），统计一律走 `psql --csv` 子进程，不要引 psycopg2/pandas DB 读取。
