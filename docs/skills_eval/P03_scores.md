## 三、裁决

**胜者：P03-2**

**差距幅度：2 分（16 vs 18），差距在「方法纪律」与「备选与不确定性」两维各 1 分。**

**差距理由**：

1. **方法纪律（+1）**：P03-2 做了 P03-1 缺失的阈值敏感性分析（§8：阈值取 60/240/480 min 结论均不变），且附录 A 给出 4 条独立复现命令，任何 agent 可在同一快照复算。P03-1 的 `fig_queue_stall.py` 虽好，但依赖 `build_report.py` 的模板渲染，复现链路更长。

2. **备选与不确定性（+1）**：P03-2 的 §7.2 推断 2 明确标注「推断，未实跑验证」，§7.3 未知项 4 条且每条标注「未查/未证」；§9 局限 6 条。P03-1 的 I2（45 张是「无真认领者」而非「池子太深」）虽逻辑合理，但未做反证（如：如果池子深，其他车道也应该有延迟，但其他车道 0-1 min——这是间接证据，非隔离实验）。

3. **额外优势**：P03-2 覆盖了同构次队列 `tensor_executions`（§B），这是 P03-1 未涉及的同类风险面；P03-2 的 `paths.md` 提供 file:line 级坐标，后续 agent 可直接跳到代码行。

## 四、各自最要害的一条缺陷（败因记录）

### P03-1 最要害缺陷
**推断链未闭环**：I2 声称「45 张 glm-5.1 单是「该车道无真认领者」而非「池子太深」」，依据是「同时刻其他车道认领延迟 0–1 min」。这是**对比论证**而非**隔离验证**——如果其他车道也恰好拥堵（概率低但可能），结论就错了。P03-1 未做「glm-5.1 车道独立排队深度分析」（如：该车道队列是否异常深？），仅靠横向对比下结论。

### P03-2 最要害缺陷
**openhands runner 引脚分析浅层**：P03-2 发现 6 张 `runner='openhands'` 单被 `runner='native'` 硬编码挡在门外（§3），但仅用 `ops/tp_worker.py:551-560` 一行代码佐证，未深入分析「为什么 openhands runner 的 daemon 不存在」——是配置遗漏？是历史遗留？还是故意不部署？这 6 张单与 45 张 glm-5.1 单是否同源？P03-2 未深挖。

## 五、事实 / 推断 / 未知 三分列（综合两份）

### 已证实（两份一致，可复算）
1. 本仓无 HTTP 202 出边（全仓 grep 0 命中）
2. 受理返回 200 + `{"status":"queued"}`（`tensor_missions.py:189`）
3. claim SQL 为等值合取过滤，无兜底分支（`:571-585`）
4. lazy reap 只处理 `claimed/running`，对 `queued` 无超期（`:541-550`）
5. `awaiting_acceptance` 需 ADMIN `decide` 才能终态（`tensor_approvals.py:229-250`）
6. 孤儿引脚审计纯函数 `pin_audit` 已存在但无调度挂载
7. 现场快照：queued 51-53 张，其中 45 张 `model='glm-5.1'`（最老 668-725 min），6 张 `model IS NULL` 或 `runner='openhands'`

### 推断（有强证据但未隔离验证）
1. 用户「202」= 口语化 Accepted 或第三方网关改写（I1）
2. 解钉 `model=NULL` 后单会被公共池领走（未实跑）
3. `tp-gen-4` 注册 model 与实际 `--model` 参数漂移（同源但注册表未逐行核对）
4. 依赖门会让下游单一起卡住（结构风险，本快照未见）

### 未知（证据不足）
1. 用户具体 mission_id/时刻（两份均未提供）
2. `awaiting_acceptance` 历史卡滞分布
3. 跨节点是否有 glm-5.1 daemon（仅本机 `ps`）
4. healer `--apply` 是否曾运行过
5. 45 张 glm-5.1 单的业务归属（是否应作废）
