## 2. 怎么做的

1. **口径判据先于实现**：三档「工件在」机检
   - `strong`：判定记录 evidence（entry/tests/impl_files/repro_cmd…）或 `result.changed_files`
     的工件指针**至少一条磁盘可解析**；
   - `medium`：指针全失效但 `head_commit` 在该仓 git 历史可达；
   - `none`：两者皆无 ⇒ 工件不可证，**不计通过**（不猜、不补）。
2. **快照闸门**：`T0` 取 DB 时钟，全集按 `created_at <= T0` 截断——系统在线推进，
   不截断则每次运行分母都变（首次实现遗漏此点，两次运行分母 82→84 漂移，已修）。
3. **零手抄**：所有数字由 `runs/m15121_kpi_repro/measure_kpi_repro.py` 程序化产出，
   同时落 `measure.sql`（SQL 原文，T0 已代入）、`psql_raw.json`（原始返回）、`rows.jsonl`（逐任务明细）。
4. **独立复核**：`runs/m15121_kpi_repro/verify_kpi_repro.py` 四路复算
   （V1 SQL 两写法 CTE/LATERAL 交叉、V2 明细重算+算术自洽、V3 固定种子抽样 20 条重探工件、
   V4 缺口台账算术），19/19 通过。
5. 计算环境：本计量依赖 **控制机侧** PG socket 与 agent worktree/git 仓，集群节点无该数据面，
   故递交集群仅作环境探针（cj985）不承载本计量；本地执行为 1 次只读 SELECT+FTS 探测（<2 s），
   非重计算，不违背「重计算上集群」纪律。

## 5. 注意点

1. **在飞任务不能算失败**：首版未排除未终态任务，两个新派审计单（15135/15136，running）
   把分母从 82 推到 84、通过率从 74.39% 掉到 72.62%；已改为「终态+快照」双闸门并单列 in-flight。
2. **「工件在」不可证 ≠ 工件不在**：18 例 `none` 中 8 例 succeeded 者历史上确有真交付
   （报告行可查），只是指针与 worktree 都没了。主值取保守口径，同时给上界，两者都如实披露。
3. **口径指向的通道是空的**：`tensor_repro_verdicts`/`repro_verdict_votes` 0 行，
   复现官判定实际落在 `tensor_maturity_verdicts`(208 行)。KPI 若按字面口径取数会读到 0/0。
4. **指针字符串噪声**：evidence 里混有 `path.py::test_name`、`{a,b}.py` 花括号、`(4/5`、`OUT=` 等
   非路径串，直接 `Path.exists()` 会系统性低估可解析率；本实现做前缀/行号/括号剥离，未做花括号展开
   （故 65.28% 仍偏保守）。
5. **结构不可逆约束**：`tensor_repro_verdicts` 有 no-delete/no-update 触发器，补录历史判定只能 INSERT。
