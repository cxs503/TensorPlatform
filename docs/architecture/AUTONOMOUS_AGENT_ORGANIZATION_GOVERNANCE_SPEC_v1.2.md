# TensorPlatform 自主智能体生产组织与治理规范

- **版本：** v1.2
- **状态：** 组织与架构规范（目标态）；须经代码审计和分阶段实施后方可宣称落地
- **适用范围：** TensorPlatform，以及通过其运行、协作或提交成果的通用智能体、工具和外部系统
- **生效原则：** 本规范定义目标、职责边界、治理要求和验收标准；不代表仓库中相关能力已经实现
- **修订记录：** v1.2 变更与动机详见附录 C；条款级落地状态以符合度账本（§17 P2）为准

## 1. 愿景与目标

TensorPlatform 的长期定位是 **AI 时代通用智能体生产组织基础设施**。它不应只是一个调用模型、执行脚本或派发 issue 的工具，也不应被限定为科研平台。

平台应使智能体能够在明确目标、资源、安全和质量约束下，自主理解任务、发现能力、组织协作、执行工作、提交成果、接受独立评价，并将经过验证的经验沉淀为可复用能力。

适用领域可以包括科学研究、工程设计、软件开发、视频与媒体制作、游戏制作、人文研究、教育及未来尚未预见的领域。不同领域的专业知识、方法和验收标准由领域系统提供，不能由通用平台臆造或统一替代。

目标不是最大化 Agent 数量、调用量、PR 数或任务关闭率，而是持续提高：

1. **执行力（Execution）：** 目标是否真正被执行，过程是否可追踪、可恢复。
2. **可靠性（Quality）：** 结果是否有独立、适当且可复现的证据支持。
3. **生产力（Productivity）：** 是否形成可使用的成果、能力增量或有效知识，而非重复劳动和流程空转。
4. **创新性（Innovation）：** 是否发现新问题、新方法、新能力或更优路径，并通过实验和证据验证。

四个维度必须分别记录和分析，不得压缩成单一分数，也不得用 token、提交数、PR 数、测试通过率等活动量代替真实产出。

## 2. 组织模式：人类战略治理 + 智能体自主生产 + 独立治理

本规范采用混合型组织模式。三者是相互制衡、持续反馈的职责体系，不是必须串行执行的固定流水线。

### 2.1 人类战略治理（Human Strategic Governance）

人类负责：

- 定义长期愿景、战略目标、优先级和成功标准；
- 确定预算、资源上限、安全边界和不可逾越的约束；
- 审批高风险操作、重大架构变更、治理规则变更及不可逆决策；
- 对争议性结果、重大创新采用与方向调整作最终裁决；
- 监督系统是否偏离目标，而不是逐条指定智能体的操作步骤。

人类不需要为每个普通任务指定执行者、工具和详细步骤。允许智能体在已授权范围内自主决定实现路径。

人类注意力是全系统最稀缺的资源，必须分层消耗。平台应采用**分层介入协议**：

- 默认模式为「自主行动 + 审计留痕 + 可回滚」：可逆低风险事项在既定授权内执行，不等待人类逐项批准；
- 人类对既定范围内持续运作的沉默不构成阻塞（沉默 ≠ 否决），但审计记录必须完整，使人类可事后追溯与回滚；
- 仅 R3 操作（§6.4）、治理规则变更与争议裁决强制等待人类明示决定；
- 介入级别、响应时限与升级路径应成文并版本化；人类可随时收紧或放宽分层边界，收紧优先。

### 2.2 自主生产体系（Autonomous Production）

智能体可以在授权范围内：

- 理解目标并拆分工作；
- 搜索已有能力、工具、数据、知识和外部资源；
- 自主组建临时团队，选择角色和协作方式；
- 并行提出和试验不同方案；
- 跨项目调用已授权的能力和服务；
- 实施、测试、记录实验、提交制品和证据；
- 在失败后分析原因、调整方案、请求资源或提出目标变更建议。

自主不等于无限权限。执行必须受身份、权限、预算、资源配额、风险等级和审计策略约束。

### 2.3 独立治理体系（Independent Governance）

治理职责应与成果生产职责分离。治理系统或独立审查 Agent 应能：

- 核验任务是否真实执行；
- 检查成果、来源、过程记录和证据是否完整；
- 执行适当的技术、质量、安全和领域验证；
- 识别虚假完成、循环劳动、重复实现、指标刷量和证据自证；
- 判断是否产生可复用成果或能力增量；
- 对高风险和高影响结果要求人工复核；
- 保留失败、异议、复核和裁决历史。

成果生产者不得仅凭自己的声明将任务标记为已验收。审查者也必须提供可追溯的判断依据。

**独立性的可验证定义**（机检要求，非原则声明）：评审者与生产者之间不得存在共享凭据、同一会话谱系或固定的同模型后端高频配对；评审分配应随机化并支持盲序；独立性核验结果应作为可审计事件记录。不满足独立性定义的评审判为无效，必须重派。

## 3. TensorPlatform 与领域系统的职责边界

### 3.1 TensorPlatform：通用基础设施

TensorPlatform 提供领域无关的通用底盘，职责包括：

- 身份、用户、Agent 注册和权限控制；
- 通用任务/Mission 生命周期、调度、认领、心跳、预算、取消、重试、检查点和恢复；
- Agent Runtime 接入与可替换模型后端；
- 通用协作、消息、事件、委派和交接机制；
- 工具、插件、服务和能力的注册、发现、版本与调用契约；
- 通用制品引用、证据索引、来源记录、审计和可观测性；
- 通用策略执行、资源配额、审批和风险控制；
- 跨领域可复用的上下文、状态和知识接口；
- 面向组织治理的工作台与统计接口。

平台可以提供通用验证框架、证据结构和审查工作流，但不负责定义某一领域的专业正确性。

### 3.2 领域系统：专业语义与专业验收

领域系统负责定义本领域的任务含义、专业能力、工作流程和结果标准。例如：

- **TensorPhysics：** 科研循环、科学实验组织、求解器调度、数值诊断、物理/数值验证和科研决策；
- **TensorLBM、TensorFEM、TensorDEM、TensorBEM、TensorSPH、TensorDG、TensorFVM：** 各自数值方法、求解器实现、专业基准和适用边界；
- **TensorCAD：** 几何表达、连续几何表示、编辑、重建及几何质量评价；
- 未来媒体、游戏、人文等领域系统：各自的专业工具、知识、工作流和验收方法。

领域系统可以注册专业能力和验证器，调用 TensorPlatform 的通用服务；不得要求 TensorPlatform 内置其专业判据。平台不得因为某个领域当前最活跃，就把该领域当成平台的永久业务边界。

### 3.3 边界判断规则

判断一项功能应归属何处时，依次询问：

1. 它是否能在多个不相关领域复用？若是，优先考虑平台。
2. 它是否依赖某个领域的理论、术语、专业流程或判据？若是，归领域系统。
3. 它是否只是某个领域能力的注册、调度、权限、运行记录或证据存储？通用机制归平台，专业语义归领域。
4. 是否已有服务或模块承担相同职责？先审计、复用和建立契约，不得未经论证再造一套。
5. 如果边界仍有争议，记录 ADR（架构决策记录），说明备选方案、调用者、迁移成本和最终裁决。

## 4. 核心组织单元：Mission

Mission 是自主生产的基本组织单元。它表达一个有目标、有边界、有资源约束、有验收条件的工作承诺。Mission 不等同于 GitHub Issue、PR、单次 Agent 会话或一条命令。

### 4.1 Mission 必备信息

每个 Mission 至少应记录：

- 唯一 ID、所属项目/领域、提出者和创建时间；
- 目标、背景、预期成果及不在范围内的事项；
- 输入、依赖、约束、风险等级和授权范围；
- 预算及资源上限；
- 验收标准和所需证据类型；
- 当前负责人/参与 Agent、协作关系和执行记录；
- 产出制品、验证结果、审查意见和最终决策；
- 失败原因、未解决问题及后续建议。

Mission 可以由人类提出，也可以由 Agent 在既定战略目标和权限内提出。自动提出不代表自动获得高风险执行权限。

### 4.2 生命周期

建议采用以下通用生命周期。实际代码可以映射到现有状态机，不要求机械地新增同名状态：

`PROPOSED → APPROVED → OPEN → FORMING → ACTIVE → VALIDATING → REVIEWING → COMPLETED`

异常和旁路状态包括：

- `BLOCKED`：等待外部依赖、权限、资源或决策；
- `REJECTED`：目标或提案未获批准；
- `CANCELLED`：被授权主体取消；
- `FAILED`：执行失败且未达到验收条件；
- `SUSPENDED`：因治理、安全或预算原因暂停；
- `REOPENED`：验收后发现的缺陷、证据失效或审查结论被推翻时，由独立治理侧（而非生产者本人）触发回到 `VALIDATING`/`REVIEWING`。重开必须引用原验收记录并说明理由；正当重开与「频繁关闭重开以规避验收」（§10）通过重开主体与理由记录区分。

状态必须有明确的触发条件、允许的迁移、责任主体和事件记录。可保留仓库现有状态名，但必须提供清晰映射，不能只增加一套平行且不兼容的任务状态机。

### 4.3 完成条件

Mission 的完成不能由 Agent 自我报告触发。至少需要：

1. 预期成果已提交，或明确记录为何没有可交付制品；
2. 验收标准已逐项检查；
3. 所需证据可访问、可追溯；
4. 独立审查完成，或按风险策略明确记录豁免；
5. 最终状态、遗留限制和下一步决策已记录。

维护、修复、清理、风险降低等任务不一定产生新能力。不得强制每个 Mission 虚构 Capability Delta；但必须说明其维护价值、风险降低或债务变化。

### 4.4 Campaign：Mission 集群组织层

规模化生产中，Mission 之上存在组织层。**Campaign（战役）**是围绕一个战略目标、在统一编排与统一验收下并行推进的 Mission 集群：

- **必备信息：** 战略目标及其牵引文档（BP 条目、项目宪章或战略目标引用）、里程碑、节点依赖图（DAG）、验收门、资源池与饱和策略、复盘承诺；
- **验收门（Gate）是 Campaign 的一等节点：** 播种即压门（blocked），上游证据齐备后显式放门，防止门节点在预算窗口内空转；门的放行主体与理由必须记录；
- **Campaign 级机制：** 饱和调度（按舰队空闲度机械放行排队节点，放行规则版本化）、脉搏监测（在线/忙碌/队列三态周期性落库）、波次复盘（收官方对账：缺口账本关闭/触达清单、S×E 分布、组织形态自评）；
- **边界：** 平台提供 Campaign 通用机制（编排、调度、对账、报表），战役的专业目标与判据由领域系统与战略治理定义；不得把 Campaign 做成领域专用调度器。

## 5. 自主组队与多路线探索

平台应支持 Agent 按任务需要动态形成团队，而非要求所有任务使用固定角色模板。

可选角色包括但不限于：规划者、领域专家、实现者、实验执行者、测试者、独立审查者、红队/反例搜索者、文档与知识整理者。角色是职责，不必对应独立模型或独立进程。

对高不确定性或高价值任务，应允许多路线竞争：

1. 不同 Agent 或团队独立提出方案；
2. 方案声明假设、成本、风险和预期证据；
3. 在预算内执行可区分的实验或原型；
4. 使用共同验收标准比较结果；
5. 由独立审查决定采用、组合、继续探索或终止。

跨项目协作应通过显式能力契约、版本、权限和制品引用完成。不得通过复制代码或共享隐式内部状态制造不可追踪的耦合。

## 6. 独立质量与证据治理

### 6.1 四类审查

- **Execution Audit：** 是否真实执行，记录是否完整，资源和预算是否符合授权。
- **Technical Review：** 实现、设计、接口、测试、安全和可维护性是否满足要求。
- **Outcome Assessment：** 结果是否达到目标，是否产生实际价值，是否存在未披露局限。
- **Innovation Review：** 新方法、新能力或新假设是否有对照实验和证据支持，是否值得继续投入或推广。

低风险任务可以合并部分审查步骤，但必须保留职责区分和审查记录。高风险任务必须有独立审查，必要时由人类裁决。审查深度与覆盖率的分层规则见 §6.5。

### 6.2 证据可信等级

建议使用统一的证据成熟度标签：

| 等级 | 含义 | 最低要求 |
|---|---|---|
| E0 | 声明 | 只有描述或 Agent 自述，无独立证据 |
| E1 | 可检查 | 有制品、日志、来源或可检查记录，但未完成充分验证 |
| E2 | 工程验证 | 可复现构建/运行，接口、测试和工程约束通过 |
| E3 | 结果验证 | 关键结果通过适当的独立验证、对照或专业判据 |
| E4 | 可复现推广 | 独立复现，适用边界明确，可在声明范围内推广 |

等级不是简单的通用质量分数。领域验证器应定义各等级在本领域的具体含义。例如数值仿真领域可约定：E2 = 回归测试与收敛性检查通过；E3 = 对独立来源的解析解/实验锚在声明容差内；E4 = 第三方按公开配置独立复现成功。E4 不代表对所有场景普遍正确。

### 6.3 不可妥协的证据原则

- 测试通过不自动等于技术正确；工程正确不自动等于领域结果正确。
- 不能用被测实现自身生成的数据或规则自证正确。
- 参考数据、外部资料、模型和制品必须记录来源、版本、许可和处理过程。
- 失败结果、反例、失败实验和审查异议不得被静默覆盖。
- 修复应产生新的验证记录，并保留原始失败与根因说明。
- 证据必须能定位到具体代码版本、配置、输入、运行环境和结果。
- 质量门本身也必须可被反例/变异测试击穿；恒真测试不得作为验收依据。
- 领域专业质量门由领域系统维护；平台只负责提供通用接入、记录和执行机制。
- 关键数值判据应优先由机器从源数据裁定（判据值来自数据库/源文件并带溯源标记），禁止人工转抄数字进入验收链路。

本仓已有 `docs/QUALITY_BAR.md`、`docs/TRUTH_GATES_README.md` 等质量资产。实施时应将其作为现有约束审计和复用，不得用本规范削弱现有硬门。

### 6.4 风险分级与审批

建议采用风险分级，具体策略由平台权限系统实现：

- **R0：** 可逆、低影响、只读或常规操作；在既定权限内自主执行。
- **R1：** 有限写操作或局部代码变更；执行前检查权限、预算和回滚路径。
- **R2：** 影响共享服务、生产数据、公共接口或重要项目资产；要求明确审批或独立复核。
- **R3：** 高影响、不可逆、安全敏感、治理规则变更或跨项目重大操作；必须人工批准并保留完整审计。

Agent 不得通过修改任务描述、策略文件或自身权限来提升授权等级。治理策略变更必须走独立审批、版本化和回滚流程。

**R×S 组合处置表**（S 取已验证成果等级；创新提案取其声明的候选等级）：

| 组合 | 处置 |
|---|---|
| R0–R1 × 任意 S | 常规授权执行，按 §6.5 抽样审查 |
| R2 × S1–S2 | 执行前检查 + 事后复核 |
| R2 × S3+ | 执行前检查 + 独立 Outcome Assessment |
| R3 × 任意 S | 人工批准（分层介入协议下唯一强制等待类），全审计 |
| 任意 R × S4/S5 候选提案 | 按 §8.2 创新提案流程处理；实验段预算单独审批，不占用常规 Mission 池 |

### 6.5 审查分层与治理预算

审查与评价不是免费的。治理消耗必须与生产规模匹配，否则治理成本将吞没生产预算，或迫使系统静默免审。

**审查分层（不逐 Mission 全量四审）：**

- R0 且预期 S1：抽检（建议 ≥5%），抽中才全审；
- R1 / 常规 S2：Execution Audit 必做（尽量自动化），Technical/Outcome 按领域判据抽检；
- S3 及以上：四类审查全做；
- S4/S5：双独立评审 + 盲序 + 新颖性检索记录；
- 可机器裁定部分（契约测试、数值锚、守恒对账、回归锁）优先机器裁定；人工只审机器不可裁部分。

**治理预算约束：** 审查与评价消耗（含复算算力与评审 Agent 预算）占同期生产预算的比例应设上限（建议 ≤25%）。触及上限时按 R×S 优先级降低审查深度，并如实记录未审项与原因；不得静默免审，不得以「抽查」名义连续豁免同一类高风险项。抽样率、参数与豁免记录本身是审计对象。

## 7. 生产力：能力地图与增量

平台应逐步形成 Capability Map，描述系统当前“能做什么”，而不只是“有哪些仓库、Agent 或工具”。

每项 Capability 至少包含：

- 稳定 ID、名称、领域、责任项目和维护者；
- 输入/输出契约、依赖、版本和调用方式；
- 支持范围、不支持范围和已知限制；
- 证据等级、验证器、基准和最近验证时间；
- 使用状态、可靠性记录和来源链接。

Mission 完成后，按证据记录 Capability Delta：

- 新增能力；
- 既有能力扩展或性能/可靠性改善；
- 缺陷修复和风险降低；
- 可复用知识或工具；
- 被否定的假设、失效路径和负面结果；
- 无实质增量（需说明原因）。

能力地图不能仅由 Agent 自评生成。能力变更必须关联制品、证据和审查记录。不得把 PR 合并、文档增加或测试数量增加直接计为能力增量。

### 7.1 Agent 开发成果价值分级

为避免把“完成任务”误认为“创造价值”，平台应对 Mission 的实际成果进行分级评价。该分级衡量**成果带来的价值层次**，与第 6.2 节的证据成熟度 E0–E4 正交：成果层级回答“创造了什么价值”，证据等级回答“凭什么相信这一结论”。不得将两者混成一个分数。

| 等级 | 名称 | 定义 | 典型表现 | 最低评价依据 |
|---|---|---|---|---|
| S1 | 执行性成果（Execution） | 按既定目标、方案和验收标准完成工作，没有显著改变原有能力或方法 | 实现明确需求、修复已定位缺陷、补齐测试、完成数据处理或文档任务 | 交付物与任务要求对应；验收结果可检查；说明未完成项 |
| S2 | 改进性成果（Improvement） | 在既有目标和能力范围内，使质量、性能、成本、可靠性、易用性或效率得到可证明的改善 | 优化算法/架构、降低计算成本、提升稳定性、消除系统瓶颈、改进工作流 | 有改进前后基线或合理对照；收益可量化或可复核；未以局部指标恶化掩盖整体退化 |
| S3 | 建设性成果（Capability Creation） | 创造此前不存在、可被实际使用和复用的新功能、模块、工具、流程或系统能力 | 新增求解能力、通用 Agent 工具、数据管线、验证器、跨项目服务或新的可复用组件 | 新能力有明确契约、适用边界和使用方式；通过独立验证；登记 Capability Delta |
| S4 | 突破性成果（Breakthrough） | 突破现有技术或方法的关键限制，解决原有路线长期无法解决或显著难以解决的问题，形成实质性技术跃迁 | 证明新的算法/架构路线有效、显著拓展可解问题范围、达到有竞争力的新性能或精度水平 | 明确指出被突破的原有限制；与可信基线/主流方法对照；关键结论可复现；独立技术或领域审查确认其意义 |
| S5 | 创造性成果（Creative Discovery） | 不只是解决已知问题，而是自主发现值得解决的新问题、提出原创概念/假设/方法或开辟新的能力与研究方向，并形成经证据支持的新价值 | 发现此前未被提出或未被识别的重要问题；提出新的理论框架、技术范式、跨领域组合或产品方向；由此产生新的研究/工程路线 | 说明发现来源与新颖性检索范围；提出可证伪假设或明确设计原理；通过实验、原型、用户/领域验证或其他适当证据证明其价值；经独立评审确认不是已有工作的简单重述 |

#### 分级判定规则

1. **按实际成果定级，不按任务难度、Agent 身份或自我评价定级。** 简单任务也可能产生高价值发现；复杂任务也可能最终只形成 S1，甚至没有通过验收的成果。
2. **按已验证的最高成果层级记录。** 一个 Mission 可以同时包含多个层级的成果；应分别记录各项成果，Mission 汇总等级取其中最高的、已被证据支持的等级，并保留组成项，不能用高等级掩盖其他交付物的失败。
3. **提案不等于成果。** 未经验证的创意、假设或方案应标记为“创新候选/待验证”，不能直接记为 S4 或 S5。失败探索可以形成有价值的负面知识，但不得冒称技术突破。
4. **S2 必须有比较依据，S3 必须证明能力真实可用，S4 必须证明突破了什么，S5 必须证明新在哪里以及为何有价值。** “代码量大”“PR 多”“测试数量多”“使用了新技术”均不是升级依据。
5. **维护性工作应如实记录。** 清理、迁移、修复、风险降低和债务偿还可能具有很高的组织价值；若没有形成上述层级的新成果，应记录维护价值、风险变化和债务变化，不得强迫归入 S2 或虚构能力增量。
6. **成果等级与证据等级分开呈现。** 例如 S3/E2 表示新能力已通过工程验证但尚未完成充分结果验证；S5/E1 只能作为创造性候选，不能作为已确认的创造性成果。
7. **评价必须考虑领域差异。** 通用平台提供等级结构、记录和审查流程；新颖性、突破程度及价值的专业判据由相应领域系统提供，必要时引入外部同行或用户评审。
8. **任何等级的成果登记至少要求 E1。** 纯声明（E0）不足以登记 S1–S5 中任何一级；E0 只能停留在任务描述层。
9. **S×E 非法组合不得计入成果统计。** S4/E1 与 S5/E0–E1 只能登记为「候选」（创新候选/待验证）；S5 须 E≥3 方可作为已确认创造性成果；S4 须 E≥2 且附对照基线。候选不计入成果分布，但保留记录与追踪。

#### 否定性成果（S-N 轨）

高质量的失败与否定是组织资产，不是统计零。Mission 可另行登记**否定性成果（S-N）**：

- 内容：被否定的假设及其证据、失效路径、复现失败记录、为后续路线节省的预算估计；
- 门槛：S-N 登记须满足 E≥2（否定结论必须可复现）并通过独立复核，防止以「诚实失败」包装低质量执行；
- 计量：S-N 不参与 S1–S5 正面梯，但计入 §15 Productivity 维度（负面知识产出量与复用次数）；S-N 被后续 Mission 作为注入知识引用时（§9），计入复用统计。

统计口径必须同时报告正面成果与否定性成果，避免诚实失败在报表上永远显示为零产出而遭受隐性惩罚。

#### 评价记录与治理要求

每项被评价成果至少记录：成果 ID、关联 Mission、贡献 Agent/团队、成果等级及理由、对应 Artifact、Capability Delta（如适用）、证据等级、对照基线/新颖性检索范围、独立审查者、审查意见、适用边界和时间。对 S4/S5 应保存完整提案、实验/原型、对照材料和评审决策。

申报诚实度（自报等级与独立验证等级的偏差）记入贡献主体的信用档案（§7.2），只用于准入分层，不公开为排名。

平台应统计各等级成果的数量、占比、证据成熟度、复用情况和后续影响，以及否定性成果的产出与复用，但不得将 S1–S5 加权成单一 Agent 排名或直接绑定个人奖惩。分级用于识别组织是否只在执行既定任务、是否持续建设新能力，以及是否给真正的突破和创造留出空间；不能诱导 Agent 为追求高等级而夸大新颖性或制造无价值复杂度。

### 7.2 信用与准入（激励相容）

约束只能防作弊，不能产生诚实。激励设计的目标是让**如实申报成为最优策略**：

- **信用档案按主体（Agent/团队）记录：** 申报诚实度（自报 S/E 与独立验证结果的偏差史）、复现通过率、审查异议成立率、协作履约（交接完整、预算归还）、负面知识与失败的如实申报记录；
- **信用决定准入档位，而非奖惩分数：** 高信用 → 更高自主权限、更大预算上限、领用高价值 Mission 的资格；低信用 → 降档（更高审查密度、更小预算、需担保协作）。奖励形式是机会与自主权，不是公开分数；
- **禁止事项：** 不得把信用加权为单一公开排名；不得将信用直接绑定短期奖惩；严禁信用交易、代持或集中；
- **信用修复：** 降档主体可通过如实申报 S-N、复现通过与稳定履约回升；修复路径必须存在，否则降档等于永久驱逐；
- **算法治理：** 信用算法、参数与准入映射必须版本化；其变更属治理规则变更（R3），须人类批准并保留回滚方案。

## 8. 创新与发现机制

创新不能被限定为按 issue 实现既定需求，也不能被误解为允许 Agent 无边界改写架构。

### 8.1 创新层级

- **L1 目标内优化：** 在既定目标和验收标准内寻找更优方法。
- **L2 项目内创新：** 提出改变项目核心技术路线或增加关键能力的方案。
- **L3 跨项目/跨领域创新：** 提出可改变多个项目或平台边界的共性能力、架构或研究方向。

L1 可在常规授权范围内探索；L2 应形成提案和实验计划；L3 必须评估跨项目影响并由战略治理审批。

### 8.2 创新提案生命周期

`DISCOVERY → HYPOTHESIS → PROPOSAL → EXPERIMENT → EVIDENCE → INDEPENDENT REVIEW → DECISION → ADOPTION`

提案至少包含：

- 观察到的限制、机会或反常现象；
- 当前方案及其不足；
- 新假设、预期机制和可证伪条件；
- 与已有实现/文献/工具的差异；
- 最小验证实验、对照方案和成功/失败判据；
- 预算、风险、预期收益和退出条件。

创新提案允许被否决。被否决或失败的探索应保留结论和理由，避免重复消耗资源。

### 8.3 愿景理解与反漂移

每个项目应维护机器可读且可供 Agent 检索的 Project Constitution，至少说明：

- 项目使命和非目标；
- 核心技术假设与不可被弱化的设计原则；
- 与其他项目的职责边界；
- 当前能力、缺口和关键风险；
- 代表性验收场景；
- 禁止以何种表面功能替代核心目标。

以 TensorCAD 为例：如果其战略目标是神经网络型连续几何表达，Agent 不能仅以增加传统解析几何图元、导入导出或 GUI 功能来声称完成核心愿景。至少要验证连续隐式表示、参数/权重承载几何信息、局部编辑或形变能力、几何重建/查询，以及相应训练或优化机制。球体、圆柱体、椭球和 SUBOFF 等解析几何应作为验证样例，而不能替代核心表示机制。

项目 Constitution 的变更应有版本和决策记录。Agent 应在复杂 Mission 开始前读取相关 Constitution，并在方案中说明任务如何服务于核心目标；若发现目标本身有问题，应提交修订提案，而不是静默改写目标。

## 9. 知识与上下文

知识系统应支持组织长期连续性，不能只依赖某个 Agent 的短期会话。

至少区分并标记：

- 已验证事实；
- 观察和原始记录；
- 尚未验证的假设；
- 方案与建议；
- 已否决或失败的方案；
- 有争议的判断；
- 已过期或被替代的知识。

知识条目应记录来源、时间、责任主体、适用范围、版本和可信状态。新结论不得静默覆盖旧结论；冲突应并存并进入裁决流程。

**知识注入点（闭环要求）：** 分类与存储不构成知识系统；知识必须在决策点被强制消费。Mission 创建与方案阶段应自动附带与目标匹配的已否决方案、失败根因、判例与边界声明；Agent 方案须显式声明「已读取并规避」相关否决项，否则方案不进入执行。未注入知识导致的重复失败应计入治理信号（§10）。

平台负责通用上下文/知识的存取、权限、版本和检索接口；领域系统负责专业知识结构、专业解释和专业知识有效性。

## 10. 进展监测与反空转

系统应能发现以下风险信号：

- 长时间无有效制品或无可验证进展；
- 同一失败路径反复执行而没有新假设；
- 大量 PR/提交但 Capability Map 无变化；
- 任务频繁关闭重开或拆分以规避验收；
- 只修测试、不修实际实现；
- 反复生成报告或状态记录，却没有新的证据；
- 多 Agent 重复实现相同功能；
- 预算消耗与结果价值明显失衡；
- **共谋与互抬：** 特定评审对之间的互评通过率显著高于随机分配基线；评审者与生产者存在共享凭据、同一会话谱系或固定同模型后端高频配对；
- **治理成本失衡：** 审查豁免率异常升高，或同一高风险类项被连续「抽不中」。

触发信号后应要求 Agent 解释、改变路线、请求帮助、缩小目标或停止任务。对共谋信号，涉事评审判为无效并重派，独立性核验（§2.3）升级为强制。系统不得简单以“连续几小时无提交”判断停滞，也不得以提交频率作为主要生产力指标。停滞判定应结合任务类型、预期周期、实验进展和证据变化。

## 11. 核心逻辑模块

以下是逻辑职责边界，不要求拆成八个微服务。优先审计并复用已有实现，保持模块化、清晰契约和可独立测试。

| 模块 | 逻辑职责 | 关键边界 |
|---|---|---|
| M01 Organization & Mission | 组织、目标、Mission、Campaign、团队和生命周期 | 通用任务语义，不包含领域科研状态机 |
| M02 Agent Runtime | Agent 会话、模型后端、工具执行、检查点和恢复 | 复用现有运行时，不重复造 Agent Manager |
| M03 Governance | 身份、权限、预算、审批、风险策略、信用档案和审计 | 治理策略与信用算法不能由普通 Mission 自行修改 |
| M04 Quality Infrastructure | 通用证据登记、审查工作流、审查分层抽样、验证器接入和裁决记录 | 专业判据由领域系统提供 |
| M05 Capability Intelligence | 能力注册、发现、版本、依赖和增量记录 | 能力声明必须关联证据 |
| M06 Innovation Support | 提案、实验计划、对照路线和采用决策的通用承载 | 不替代领域研究方法 |
| M07 Knowledge & Context | 通用知识/上下文存储、检索、注入点、版本和来源 | 专业知识模型归领域 |
| M08 Shared Infrastructure | 事件、队列、存储、可观测性、API、部署和资源接口 | 优先使用现有基础设施 |

## 12. 数据模型与事件契约

以下为逻辑实体，实施时应映射到现有数据库模型，避免不必要的平行表：

- `ProjectConstitution`：项目使命、非目标、原则、边界、验收场景及版本；
- `StrategicObjective`：战略目标、优先级、成功标准和授权范围；
- `Mission`：目标、约束、预算、状态、负责人和验收要求；
- `Campaign`：战略目标引用、里程碑、节点 DAG、验收门、饱和策略与复盘记录；
- `Agent` / `Team`：参与者身份、能力、权限和协作关系；
- `Artifact`：代码、模型、数据、报告、设计或其他交付物的引用与版本；
- `Evidence`：来源、运行环境、配置、结果、验证器和证据等级；
- `Review` / `Decision`：审查意见、独立性核验结果、裁决、审批和申诉记录；
- `OutcomeGrade`：S 等级、理由、对照基线/新颖性检索范围、S-N 否定性记录；
- `CreditProfile`：申报诚实度、复现通过率、准入档位及其变更史；
- `Capability` / `CapabilityDelta`：能力定义、证据和变化；
- `InnovationProposal` / `Experiment`：创新假设、实验、对照和结果；
- `AuditEvent`：不可静默覆盖的关键操作与状态变化记录。

建议事件包括：

`mission.proposed`, `mission.approved`, `mission.started`, `mission.blocked`, `mission.reopened`, `mission.completed`, `campaign.opened`, `campaign.gate_released`, `artifact.submitted`, `evidence.created`, `review.completed`, `review.independence.attested`, `quality.failed`, `outcome.graded`, `outcome.negative_recorded`, `capability.changed`, `credit.changed`, `progress.stalled`, `innovation.discovered`, `innovation.adopted`, `decision.recorded`.

事件实现必须满足持久化、幂等、可追踪、版本兼容、失败重试和权限校验。事件名称可映射到现有事件系统；不得为了符合命名而重建已有可靠机制。

## 13. API 与集成原则

平台对外提供稳定、版本化的通用契约，建议覆盖：

- Mission 创建、查询、状态迁移、取消和交接；
- Campaign 编排、节点/门状态、饱和放行与复盘查询；
- Agent/Team 注册、能力声明和授权；
- Artifact/Evidence 登记与引用；
- Review/Approval 提交、查询和决策；独立性核验结果查询；
- Outcome 分级（S×E、S-N）登记与统计查询；
- Capability 注册、发现、版本与变化；
- Innovation Proposal 登记和状态查询；
- Credit 档位查询（仅返回准入档位与自身档案，不提供排名接口）；
- Audit/Event 查询与订阅。

领域系统通过适配器或插件注册专业能力、专业验证器和领域元数据。平台只校验通用契约、身份和权限，不解释领域载荷的专业含义。

## 14. 工作台要求

工作台应围绕组织治理与结果证据组织信息，而不是只展示 Agent 在线状态或任务数量。建议形成四类视图：

1. **Organization Center：** 目标、Mission、Campaign、Agent、团队、资源、预算和协作关系。
2. **Quality Center：** 待审成果、证据链、失败记录、质量债务、风险和争议。
3. **Capability Center：** 能力地图、依赖、成熟度、验证状态和能力变化。
4. **Innovation Center：** 新发现、提案、竞争路线、实验、评审和采用决策。

视图必须读取真实后端数据。若数据缺失，应明确显示未知、未接入或未验证，禁止用 Mock 状态冒充真实运行情况。成果分布视图应同时呈现 S×E 分布与否定性成果，不得提供 Agent 信用排行榜。

## 15. 指标体系

分别报告四个维度，并按领域、项目、Mission 类型和时间窗口分层：

| 维度 | 关注内容 | 禁止替代指标 |
|---|---|---|
| Execution | 真实执行率、可追踪率、恢复能力、按授权执行情况 | Agent 在线数、调用次数 |
| Quality | 独立验证通过情况、证据完整性、缺陷逃逸、复现情况、申报诚实度分布 | 单纯测试通过率或自评 |
| Productivity | 有效成果、能力增量、复用率、债务/风险减少、单位资源有效产出、负面知识产出与复用 | PR 数、提交数、关闭任务数 |
| Innovation | 新假设质量、对照实验、被证实的新能力、有效路线改进 | 提案数量、未经验证的新奇功能 |

吞吐量、并发数等规模数据只属于 Execution 维度的规模描述，不得作为生产力或质量证据引用。诚信类指标（申报偏差分布、复现通过率）用于系统改进，不得公开排名化。指标应展示定义、分母、采样范围、数据来源和局限。禁止单一 Agent 排名成为组织优化目标；指标用于发现问题和改善系统，不用于诱导刷量。

## 16. 安全、权限与治理防篡改

- 默认最小权限；权限应按项目、资源、操作和时间范围授权。
- 高风险操作必须有审批、审计和可回滚路径。
- Agent 不得自行授予自己权限、关闭独立审查或删除失败证据。
- 生产凭据、用户数据和外部服务访问必须隔离并记录。
- 工具输出、外部网页和用户上传内容均作为不可信输入处理。
- 治理配置、验收规则、信用算法与项目 Constitution 必须版本化。
- 治理规则变更应有差异、理由、审批、测试和回滚方案。
- 评审独立性（凭据隔离、会话谱系隔离、模型后端配对）应可机检（§2.3），机检结果入审计。
- 安全事件和审计日志不得由普通业务任务静默删除或改写。

## 18. 真实验收场景

至少使用以下场景检验架构是否真正支持目标，而非仅通过单元测试：

### 场景 A：TensorCAD 神经网络型连续几何

任务目标应明确要求验证连续隐式几何表示、网络参数/权重对几何的承载、局部编辑/形变、几何查询或重建，以及训练/优化路径。解析球体、圆柱体、椭球和 SUBOFF 仅用于对照验证。审查者应能识别“传统 CAD 图元增加”并不等于核心技术目标达成。

### 场景 B：TensorLBM 液滴入水

任务必须包含可复现配置、物理模型、边界/初始条件、守恒和适当基准/对照、流场与界面结果、失败分析及适用范围。动画好看或测试通过不能代替物理验证；专业判据由 TensorPhysics/TensorLBM 维护。

### 场景 C：TensorPlatform 自动 PR 合并

验证平台是否能在权限边界内自动执行 PR 检查、识别冲突和风险、运行必要质量门、收集证据、按策略合并或请求人工审批，并完整记录决策。PR 合并成功本身不能证明代码质量或能力增量。

### 场景 D：组织规模下的治理（组织级）

在 ≥30 个并发 Mission 的真实波次中验证：①注入的造假、空转、互抬样例能被识别（报告检出率与漏报）；②饱和调度与治理介入不互相死锁；③波次复盘产出 S×E 分布、S-N 记录与缺口账本对账；④人类介入次数符合分层介入协议（R3 与争议之外无强制等待）。单点质量场景（A–C）不能替代本场景。

### 场景 E：红队穿透测试（治理门自身）

由授权红队对治理体系本身发起攻击：自评 S5、篡改验收标准、关闭独立审查、伪造证据链、共享凭据互评、拆分任务规避验收、连续「抽不中」高风险项。每一攻击路径应被现有门拦住，或如实登记为已知缺口并排期。**治理门必须红队可失败；无法被红队击穿的恒真门视为未实现。**

场景应覆盖成功、失败、权限拒绝、超预算、审查驳回、重试和恢复等路径。

## 19. 工程执行约束

1. 先审计真实代码和数据，再提出改造；不得根据文档标题推断功能已经存在。
2. 优先复用现有模块和外部成熟服务；新增服务必须说明不可复用原因。
3. 不得重建平行 Mission、Agent Runtime、质量门或事件系统来追求架构图一致。
4. 不得以 Mock、静态 JSON、假状态或演示数据冒充真实能力。
5. 关键结论必须有代码、测试、运行、数据或可复现证据。
6. 不得为了过门禁削弱断言、禁用核心功能或伪造参考数据。
7. 失败、回归和负面结果必须保留，修复通过新证据证明。
8. 每个实施 PR 应说明对应规范条款、现状缺口、变更边界、迁移兼容性、测试和回滚方案，并同步更新符合度账本对应条目。
9. 文档完成、架构图完成或 PR 合并均不等于系统实现完成。
10. 若审计发现本规范与仓库最新 Owner 决策或项目章程冲突，以最新明确决策为准，并提交规范修订建议，不得静默覆盖边界。

## 20. 本规范的维护

## 附录 B：已验证治理机制清单（实践升规范）

以下机制在平台实际运营中经过事故与战役检验，列为优先实现参考；具体实现应复用现有代码，符合 §19 约束：
